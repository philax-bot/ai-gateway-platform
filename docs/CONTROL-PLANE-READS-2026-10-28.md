## 已定位与实现

同一开发数据库端点、4 用户 / 并发 4 / 60 秒：[基线](validation/reads-2026-10-28/baseline-c4-u4.json) 的状态读取 P95 606.68ms，维护 P95 2149.84ms。工作区读取 P95 511.75ms、最大 1924.67ms；连接池等待 P95 0.17ms。慢读包含完整工作区往返，不能把 SQL 墙钟时间直接解释为数据库执行时间。

认证现在只读成员、组织和会话；维护预检查与监控采集只读所需的九个字段。SQL 在数据库内过滤 JSON 对象，保留显式 null 与可选字段缺省；没有使用会递归删除业务 null 的转换。内存读取保持独立副本。字段列表只由内部方法提供，不接受请求参数选择字段。样本完整工作区 43583 字节，认证投影 3949 字节，维护投影 7036 字节，分别减少约 91% 和 84%。

会话每次仍从当前数据库读取，不缓存权限；成员、祖先组织停用、会话撤销即时影响后续读取。月度发放、监控和保留清理仍在各自事务内读取完整状态并重新检查当前条件；没有复用旧快照跳过这些检查。状态接口保留原有 200 条调用记录和汇总范围，HTTP 输出、调用分页、金额、告警分母及失败质量语义不变。此次不修改数据库结构或锁协议。

`workspace-read.spec.ts` 验证实时角色 / 组织 / 会话撤销、无关历史排除、null / 缺省和独立副本。PostgreSQL 策略锁检查额外验证持有运行行锁期间精简读取仍可完成、数据库 null / 缺省保持，以及提交后的撤销可见。

## 回归中发现的验证缺口

首次内存 HTTP 回归为 369 项，低于上轮的 371。排查发现旧 `check-metered.mjs` 只有在本轮流量已经进入关闭分钟窗口、实际产生告警时才执行知晓 / 通知断言；较快的内存流程可能全部落在当前分钟，因此跳过两条验证。现在将已有历史待核对调用的测试完成时间明确设置为两个分钟前，并强制断言告警存在，再执行知晓与通知检查。没有增加模型生成、等待跨分钟或改变生产时钟。更新后内存完整 HTTP 372 项通过。这些计数包含辅助状态读取断言，不等同于固定数量的独立测试案例。

首轮 PostgreSQL HTTP 427 项、策略锁 / 精简读取 23 项通过后，连接池专项出现一次未分类的非断言异常。旧探针只输出统一错误，无法确认发生阶段与原因；[原始失败记录](validation/reads-2026-10-28/monitoring-initial-failure.json) 保留对应本地日志位置。探针现补充固定阶段、错误类别、受限错误码及池计数，不输出私有异常文本。追加诊断后一次复测及随后连续两轮的 10 项断言均通过；**首次原因仍未确认，不能宣称已经定位或消除该异常**。未修改产品的 5 秒超时或探针原有的超时设置。
