## 3. 工作包 A：调用追溯

### 3.1 目标和契约

保留平台请求 ID，补齐上游请求号和客户端显式重试关系。首版不增加自动重试、响应正文缓存或独立链路追踪中心。

| 字段/入口 | 建议语义 |
| --- | --- |
| `upstreamRequestId?: string \| null` | 复用 `SettlementRequest` 已有字段，补入日志与持久化；从上游受支持的请求号响应头采集，未提供时为 null |
| `retryOfRequestId?: string \| null` | 新请求显式关联之前的一次调用，贯穿授权输入、预占元数据和日志；没有关联时为 null |
| `x-retry-of-request-id` | 受限的客户端输入；由网关转交控制面校验，不能直接信任或直接展示原调用信息 |

上游响应正文中的 completion ID 不自动等同于上游请求号。首版明确支持 `x-request-id` / `request-id` 的采集顺序，其他来源在实际联调时逐项登记，不做任意响应头收集。字段须限制长度、拒绝控制字符。

重试关联必须在控制面确认原请求与当前请求属于同一企业、主体类型、主体、用途及项目范围，且当前身份仍可调用。不存在和无权关联使用统一的错误语义，避免探测他人请求；不允许自引用或修改已经建立的关系。一次显式重试仍是新请求，独立授权、预占、计价和结算。相同幂等键重放继续返回原授权/结算结果，不重复调用上游。

### 3.2 实施范围

- 共享契约：`packages/contracts/src/index.ts`、`calls.ts` 和两份 `contracts/*.yaml`。
- 数据面：`services/gateway-sim/src/server.ts`，必要时调整 `journal.ts`，保证故障和重启补发时保留上游请求号。
- 控制面：`store/accounting.ts` 的幂等指纹、`demo.store.ts`、`postgres.store.ts`、`postgres-call-query.ts` 和授权入口。重试元数据纳入一致性校验；无关联请求保留原有指纹格式，有关联请求使用明确的扩展格式。不能仅追加一个 null 字段就让升级前的合法幂等键全部冲突；需覆盖已持久化旧记录的兼容用例。
- 数据库：新增迁移；不修改已执行的 001–009。旧日志字段留空，不伪造历史关联。
- 页面：`CallExplorer.tsx` 的详情区展示上游请求号、关联原调用及“查看关联调用”。读取仍走服务端职责范围，不在前端先取全量再过滤。

### 3.3 验收

1. 非流式、SSE、上游错误响应均能保留已有的请求号；未返回请求号显示“上游未提供”。
2. 同一主体/用途的重试可关联；跨成员、项目和应用的伪造关联被拒绝且不泄露原调用。
3. 重试产生独立账本变化；同键并发与结算重放不重复扣费。迟到用量和人工核对不能覆盖已有可信关联。
4. 日记重启补发、PostgreSQL 重启和历史空字段兼容均通过。新增元数据不保存提示词、回答、密钥或原始响应头全集。

## 4. 工作包 B：连接验证的计量归属

### 4.1 默认业务口径

**连接验证属于平台诊断流量，由平台承担内部成本，不扣运营个人、项目或应用额度。** 记录诊断用量和价格依据；这里的内部成本估算不是厂商账单或新的财务结算系统。

不向现有 `Purpose = personal | project | application` 添加第四种额度用途，不伪造员工身份或建立另一套钱包。复用现有金额精度、缓存子集计价等纯计算逻辑，新增独立的验证运行记录作为技术计量证据。

保留“先验证连接、再补价格”的模型配置路径：价格未知不阻止连接验证通过；显示“连接已通过，成本未知”。用量缺失也不能按零费用处理。未知字段保存 null；只有有完整依据时才记录明确的 0。

### 4.2 执行与存储

- 延续 `POST /api/v1/platform/services/:id/verify`，增加可选幂等键并保持旧调用兼容。页面一次操作使用一个稳定键；主动重新验证使用新键。同键重试不重复请求上游，重放前重新核对当前运营权限。
- 建立服务级运行及逐映射结果，至少记录：运行 ID、操作者、服务 ID、配置版本、模型映射快照、开始/结束时间、执行结果、上游请求号、输入/输出/缓存用量、用量完整性、价格快照和内部成本状态。一次服务验证中的多个映射不能合并成一个无法解释的金额。
- PostgreSQL 使用专门的验证记录表，内存模式提供等效存储；不要把持续增长的逐请求明细塞进工作空间 JSON。记录不包含正文、凭据值或完整上游地址中的敏感信息。
- 外呼前先持久化运行标识和待执行记录；外呼在数据库事务之外进行，结束后单独事务保存结果。持有工作空间锁时不得等待上游 HTTP，也不得嵌套借用连接池连接。
- 同一服务只允许一个有效验证运行；使用数据库可恢复的占用/租约，内存模式等价处理，不能只依赖单进程布尔锁。进程崩溃留下的运行恢复为“中断、用量待确认”，不自动重发可能已执行的验证请求。
- 验证中服务配置发生变化：保留旧版本运行及用量证据，不能把旧结果写为新配置已通过。日志保存失败时返回可恢复状态，不能用“验证成功”掩盖计量证据丢失。
- 运营在模型服务详情查看最近结果，并按需分页查询历史验证记录。权限只向运营开放；用户调用统计、模型业务告警分母及员工调用历史默认排除诊断流量，避免悄然改变既有统计口径。

主要入口：`platform.service.ts::verifyService`、`platform.controller.ts`、模型服务详情与 `EditorFlow.tsx`。新增技术记录存储和迁移，复用现有契约及组件，不新增顶层管理中心。

### 4.3 验收

1. 有用量/无用量、缓存子集、免费/价格未知、401/404/5xx、超时和响应不合法分别可辨认；用量与成本未知不得显示为 0。
2. 多映射部分失败时，每次已经发出的请求都有运行证据；失败后的模型不能误标为验证通过。
3. 同键重复、并发重复、进程中断和配置变更不造成重复验证或错写状态。
4. 个人、项目、应用的余额和资金账本保持不变；诊断记录不污染员工调用统计和现有业务告警分母。
5. PostgreSQL 与内存结果一致；验证记录查询遵守权限和分页约束，历史审计可追溯到运行 ID。

## 5. 工作包 C：存量方案版本迁移

### 5.1 首版迁移语义

限定为**同一方案的旧版本权益迁到当前版本，且一次性/月度类型不变**。跨方案搬迁和一次性/月度互转不在本包内，预览明确列为不适用，避免为了少量需求引入复杂周期补偿规则。

- 复用 `PlatformCommand` 的预览和执行通道，建议命令 `entitlements.migrate`；输入显式权益 ID 列表、目标方案 ID/版本和必填原因，首版最多 200 项。
- 只允许运营操作。目标方案须有效，源权益须有效且属于该方案，人员须符合现有访问条件；已经是目标版本的权益返回跳过。
- 更新权益的 `planVersion`、`planSnapshot` 与 `range`；保留权益 ID、原授予时间、到期日、来源、规则关联、已发周期及原 `futureGrants` 状态。迁移不重新启用已停止的未来发放，也不延长有效期。
- **不补差、不发新额度、不重复发本月额度。** 已发批次的余额、累计发放、到期日和资金来源保持原值；月度后续应发周期采用目标快照，一次性金额变化不追溯补发。
- 授权范围立即按目标权益与当前池规则生效，沿用 `syncResources` 更新该权益关联批次的可调用模型。因此已有资金的模型适用范围可能扩大或收缩，必须在预览中明确列出；其他权益、项目及应用不受影响。
- 已准入请求继续使用原路由、价格与资金批次完成结算。迁移影响后续新请求，不改历史调用与预占。

### 5.2 预览、执行和页面

预览显示：人员/权益、原版本→目标版本、模型新增/关闭、限制变化、未来发放金额变化、保持不变的余额/期限、受影响密钥、变更/跳过/不适用数量，并明确提示“不补发额度”。

预览签名绑定操作者、精确名单、目标版本、业务 revision 和有效期。确认时重新核权、核对目标版本和人员状态。整批事务更新、同步授权并写入逐权益审计；同键重放返回原回执。失效或不适用对象必须重新预览，不能悄悄缩小已经确认的名单。

入口放在现有方案详情或已开通权益列表，使用既有多人选择、`Modal`/`EditorDialog`、`Table`、`Status` 等组件。展示批次回执和逐人结果，不另造方案运营中心。

主要文件：`packages/contracts/src/platform.ts`、`platform.service.ts`、`workflow-actions.ts`、`command-authorization.ts`、`domain.ts`、`WorkspacePages.tsx`、`editors.ts`。先查清预览/权限现有分发位置再接入，避免只加执行分支而漏掉预览和重放核权。

### 5.3 验收

1. 一次性/月度分别覆盖成功、重复、过期、停用、已是目标版本、跨方案和跨周期类型拒绝。
2. 对比迁移前后的全部相关资金字段，确认金额、期限、来源和已发周期不变；运行月度任务不重复发已发周期。
3. 验证范围扩大/缩小、follow/specific、其他叠加权益仍有效，以及在途请求按旧快照结算。
4. 预览后修改方案/人员/职责会要求重新预览；并发提交、幂等重放和事务失败不产生部分迁移。

信息缺失只阻塞对应实接步骤。先交付脚本、配置模板和本地证据，再一次性报告缺失输入；不以等待为由停下 A–D，也不把环境开关存在当作真实请求或部署授权。

### 7.3 验收矩阵

- E：非流式、SSE、工具调用及工具结果回传、取消、超时、上游 4xx/5xx、用量缺失、缓存子集、价格快照、费用核对和请求追溯。用确定性本地工具执行工具调用闭环，不把实际业务系统调用混入兼容性测试。
- 先验证一个真实模型和一个目标客户端。目标工具若需要当前未实现的接口，记录具体缺口后补最小适配，不能根据接口名或工具名提前实现所有协议。
- F：正式空安装、浏览器登录与 TLS 信任、网络限制、停止时在途结算、进程/容器重启、数据库故障恢复、数据库与全部网关日记的联合备份恢复。
- 负载结论必须附机器配置、模型、并发、持续时间、样本数、错误率、TTFT/延迟和结算状态。无实际测量时不承诺固定 QPS，也不把五分钟吞吐当作容量上限。
- 单机试运行与多副本/跨主机恢复分别给结论。未做故障切换演练时，状态保留为“未验证高可用”，不因此阻止已经满足范围的单机试点交付。

## 8. 工作包 G：按首批客户接企业身份和通知

本包先确认客户已有能力；缺少提供方、协议和目标对象时，交付接入条件清单，不提前构建通用企业集成平台。
