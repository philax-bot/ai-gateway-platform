执行 `node scripts/check-container.mjs --keep`，本次独立项目 `atlas_check_2e6e9b47814c41dd`：**18 项隔离断言通过，检查进程正常退出**。使用本机 Docker 接口与 Compose 5.5.0，Linux 容器中的 Node.js 22.23.3、Nginx 1.30.6、原生 PostgreSQL 客户端 16.15；镜像构建锁定 pnpm 11.13.1。

## 已取得的证据

| 范围 | 实测结果 |
| --- | --- |
| 实际构建 | 从源码构建 server / web / operations 三个目标，非源码静态检查 |
| 配置排除 | server 内不存在根 `.env`、控制面 `.env` 或 `deploy/runtime.env` |
| HTTPS | 使用两天有效的 localhost 测试证书，客户端以该证书作为显式 CA 做真实 TLS 校验，取得 Web 页面 |
| 内部路由 | HTTPS 入口拒绝 `/internal/v1/policy/credentials/resolve`，返回 404 |
| 首次安装 | 正式空库要求安装口令；通过 HTTPS 创建管理员，登录返回 `Secure` / `HttpOnly` 会话 |
| 正式种子 | 初始只有一名管理员，没有演示模型、额度或其他账号 |
| 模型凭据 | 私有 raw env 文件包含字面 `$` 和 `#` 的虚拟凭据；本地替身要求精确 Bearer 值，控制面验证和网关调用均通过 |
| 正常调用 | 通过统一 HTTPS `/v1/chat/completions` 完成非流式请求 |
| 流式 | 本地替身首段后延迟 1.5 秒才发最终用量；代理客户端确实先收到分段，再收到最终用量与 DONE |
| 权威账本 | 两次 HTTPS 请求生成两条调用日志，消费原发放批次 |
| 容器重建 | 强制重建后原登录会话、同一余额和调用历史保持；网关从同一命名卷启动，outbox queued 为 0 |
| 网络 | 数据库、控制面与网关均无宿主发布端口，只有 HTTPS Web 入口发布到本机回环地址 |
| 容器内备份 | 停入口、网关与控制面，operations 容器用原生 pg_dump 归档 schema 和停止的日记卷，含 9 个迁移版本 |
| 容器内恢复 | 原 schema 仅在专属测试数据库改名保留，原生 pg_restore 到原名；日记恢复到新的子目录并重新映射网关路径 |
| 恢复后运行 | 原会话、原余额和两条日志可用；同一密钥继续完成新调用，日志变为三条 |

计数以脚本内 `check` 为准，表格合并相关检查。恢复 queued 事件的恰好一次记账、重复结算和损坏目标拒绝由另一次真实 PostgreSQL 原生恢复检查覆盖，见 [45 项安装与备份恢复检查](VALIDATION-BACKUP-2026-10-19.md)。本轮容器归档时日记已结清，不将它表述为容器内存在 queued 事件的测试。

启动检查发现并修正 Nginx 默认 fastcgi/uwsgi/scgi 临时目录与只读根文件系统冲突；所有临时目录现在写 `/tmp`。模型验证与调用分别使用原有显式外部请求开关，测试仅为自己的 Docker 网络替身开启。初次构建还发现 pnpm 11.13.0 的上游弃用告警，已锁定补丁 11.13.1。
