# AI 网关控制面与数据面架构决策 v0.1

日期：2026-10-16。状态：推荐进入 Higress 隔离 PoC，暂不锁定生产网关实现，也不修改 Higress 核心。

## 1. 决策结论

本产品采用“自有控制面 + 可替换数据面”的架构。控制面负责企业业务事实，数据面负责请求通道。Higress 作为第一候选数据面实现进行验证，但不能成为个人权益、项目额度、审批或计量账本的来源。

第一版不从零实现完整反向代理、连接管理、TLS、基础路由和通用限流；这些能力优先复用 Higress。我们自己实现策略判定、额度账本、用量结算和网关适配器。只有 PoC 证明必要的请求生命周期、流式用量或动态策略扩展无法通过插件、外部鉴权或适配器实现时，才评估 Higress 核心修改。

## 2. 分层边界

```text
管理配置路径
前端 -> 业务后端 -> 策略/额度模块 -> GatewayProvider -> Higress 配置

实际调用路径
员工/应用 -> Higress -> 请求前策略 -> 模型服务
                         |
                         +-> 请求事件 -> 用量结算 -> 调用日志/审计
```

| 层 | 主要职责 | 权威数据 |
| --- | --- | --- |
| 前端 | 运营配置、员工使用、项目与审批、状态反馈 | 无业务权威数据 |
| 业务后端 | 组织、模型目录、模型服务、模型池、权益、审批、密钥元数据 | 业务数据库 |
| 策略模块 | 判断主体、用途、模型、范围、期限和调用条件 | 策略版本与授权快照 |
| 额度账本 | 预占、结算、回滚、批次期限、幂等和审计 | 额度账本 |
| GatewayProvider | 发布路由、策略引用、凭证状态、运行状态适配 | 同步版本与结果 |
| Higress | 认证接入、代理、路由、超时、基础限流、上游观测 | 运行态配置，不是业务账本 |
| 模型服务 | 已部署的推理接口 | 上游响应与能力 |

Higress 可以拒绝一个请求，但最终的“允许使用哪个模型、扣哪个用途和额度来源”必须可追溯到控制面策略版本。Higress 配置延迟、失败或回滚时，控制面必须能显示同步状态，不得静默宣称已生效。

## 3. 为什么不直接把业务做进 Higress

- 个人额度和项目额度是不同账本，带来源、有效期、成员分配和审批结果，不是单一限流值。
- 同一员工可以有多个 API Key，但不能绕过同一用途的权益和额度；密钥数量不能成为扣费主体。
- 一次调用可能经历流式输出、上游超时、客户端取消、部分用量或计量延迟，结算需要幂等和可回滚。
- 模型池的“跟随模型池 / 仅指定模型”是产品授权语义，不能简化为一条静态路由。
- 模型池、权益和额度的历史关系必须可审计，不能依赖网关当前配置推导过去事实。

## 4. 适配器边界

业务后端只依赖 `GatewayProvider` 能力，不依赖 Higress 内部对象、数据库或管理页面结构。第一实现为 `HigressProvider`，后续可以增加其他实现。

```text
publishRoute(route, version)
publishPolicyReference(policyVersion)
revokeCredential(credentialId, version)
getSyncStatus(resourceId)
getRuntimeStatus(resourceId)
collectRequestEvents(cursor)
```

适配器必须记录：目标网关、目标资源、期望版本、实际版本、提交时间、结果、错误分类、重试次数和回滚版本。配置发布采用版本号和幂等键，不能用“最后一次保存时间”判断是否生效。

## 5. 自研与复用判断

| 能力 | 初始归属 | 说明 |
| --- | --- | --- |
| OpenAI 兼容代理、连接池、TLS | Higress | 先复用，除非 PoC 证明不兼容 |
| 模型路由和上游连接 | Higress + 适配器 | 控制面发布期望配置，运行态由 Higress 执行 |
| 认证入口 | Higress + 策略模块 | Higress 接入请求，策略模块返回业务授权结果 |
| QPS / 并发 / 超时保护 | Higress | 与业务额度分开；保留生效来源 |
| 个人/项目模型权限 | 我们的策略模块 | 返回策略版本和拒绝原因 |
| 额度预占与结算 | 我们的额度账本 | 不能只在网关插件内扣减 |
| Token 计量与费用状态 | 我们的结算模块 | 上游或网关缺数据时显示待核对 |
| 调用日志 | 我们的日志模型 | 接收 Higress 事件并补齐业务来源 |
| 运行监控 | Higress 指标 + 我们的观测 | 分开实时运行态与业务计量态 |

## 6. 什么时候才考虑改 Higress 核心

必须同时满足以下条件，才进入核心修改评估：

1. 需求是每个请求都必须具备的网关生命周期能力，而不是我们的业务规则。
2. 外部鉴权、插件、管理 API、日志扩展或旁路结算无法可靠提供该能力。
3. 缺口已经在固定版本 PoC 中复现，并有可重复测试。
4. 修改不会把额度账本、审批状态或组织模型嵌入 Higress。
5. 能维护补丁、回归测试、升级路径、回滚方案和安全响应。

优先顺序是：配置和外部鉴权 → 官方插件/扩展点 → 旁路服务 → 上游贡献 → 最小化 fork。没有满足证据时，不进入 fork。

## 7. 当前不做的事

- 不把 Higress 管理页面作为我们的运营后台。
- 不把 Higress 的路由配置当作模型池或权益数据。
- 不让前端直接调用 Higress 管理接口。
- 不在 PoC 阶段接入真实生产密钥、真实额度或生产模型调用。
- 不用一次 HTTP 200 证明请求完整成功、用量完整或额度已正确结算。

## 8. 进入实现的前置条件

- 选定一个隔离 Higress 版本和测试模型服务。
- 建立控制面内部 API 合同，见 [gateway-control-plane-v0.1.yaml](contracts/gateway-control-plane-v0.1.yaml)。
- 按 [PoC 验收清单](gateway-poc-checklist-v0.1.md)验证非流式、流式、失败、并发和配置同步。
- PoC 通过后，再确定正式前端/后端仓库、部署方式、数据存储和生产网关版本。
