# 模型接入参数边界调研与治理矩阵 v1.1

调研日期：2026-11-17。v1.1 补充边界强度与运营负担的平衡，并收紧首期范围。范围：当前工作区实现、现有本地测试、供应商官方文档。本文是方案，尚未修改运行策略或接入配置；本地证据不能证明生产环境行为。供应商示例是调研当日的特定接口规则，不是所有兼容服务的通用常量。

## 1. 结论与直接影响

目前平台具备“按平台配置限制请求、估算用量、转发请求、按实际用量结算”的基础闭环，但尚不具备完整的“具体服务 × 上游模型版本 × 协议 × 模式”的参数契约。**平台准入通过，不等于上游一定接受；上游 HTTP 200，也不等于参数实际生效。**

最需要优先处理的缺口：

1. `ModelDefinition.contextTokens` 是人工配置的逻辑模型属性，未自动核对上游部署；同一逻辑模型的不同服务可能实际只有不同的上下文上限。
2. `ModelDefinition.maxOutputTokens` 明确属于模型发现展示信息，目前不参与准入。真正执行的是 `UsageLimits.maxOutputTokens` 与上下文剩余量。
3. Chat 的大部分采样、推理、工具、结构化输出参数直接交给上游；缺少按具体模型与模式进行的范围、互斥及能力检查。
4. 多模态已有基础接入与计量，但多数规格仍未建模。ASR 默认补 `verbose_json`、Rerank 用整批文本检查统一上下文、视频只检查通用时长区间，都可能与真实服务不匹配。
5. 费用预占是估算，不是生成硬上限，也不是完整覆盖最坏费用的担保。参数治理应补足这一事实的表达，不能重新把预占估算偷偷变成生成限制。

建议采用：**平台内置硬约束 + 模板生成服务能力 + 仅在例外时人工覆盖 + 按风险处理未知项。** 服务能力过滤与版本证据保留，但由平台承担规则维护。默认不静默截断输入、不静默降低显式输出要求、不删除用户参数后重试。下面 50 项是平台内部风险目录，不是运营管理员的配置清单，也不是每次接入的实测前置清单。

### 1.1 v1.1 决策：规则可以完整，日常配置必须简短

平衡点是按“后果严重程度 × 判断依据可靠性”决定拦截强度，而不是把未知能力一律禁用。账务、权限和平台资源底线必须守住；普通兼容性失败可以由上游给出确定结果，平台负责准确转述与归因。

| 边界分层 | 例子 | 默认处理 | 谁维护 | 运营新增负担 |
| --- | --- | --- | --- | --- |
| A：平台必须守住 | 越权、未建模的候选/收费工具放大、状态串用、平台请求体/资源上限、重复生成、用量造假 | 无论供应商模板是否完整都检查；不能证明符合时拒绝相关请求/功能 | 平台代码与既有业务策略 | 无参数规则需要填写；只维护既有业务额度/上限 |
| B：已有可靠依据的硬限制 | 已确认部署上下文、输出上限、端点类型、确定不支持的格式/组合 | 拒绝或从候选服务中排除；保留明确的输入与输出承诺 | 供应商+模型/协议模板，必要时服务覆盖 | 已匹配模板时无需逐项确认；部署例外集中改一次 |
| C：只影响兼容性，依据不充分 | 新模型的 sampling/stop/schema 子集；通用 BPE 接近窗口；模板未覆盖某枚举 | 在 A 类底线满足、无已知冲突且不改变请求语义时，保持原参数交上游校验；记录未知状态 | 平台适配维护者；调用错误由应用开发者按诊断处理 | 不要求管理员研究参数；不为每次 400 生成运营待办 |
| D：效果/偏好项 | 采样推荐值、seed 尽力确定性、普通风格提示、已知无效果但无费用/承诺影响的参数 | 原样转发或提示，不仅因质量偏好阻断 | 应用开发者与模型使用者 | 不增加配置 |

参数可从 C/D 升为 A/B：例如一个扩展会增加隐含收费，或平台已经明确承诺严格 schema/完整文档，则不能再以“普通透传”规避承诺。费用放大是否已覆盖，要看平台实际计价与可承担范围；若已有明确包价方案，不强制为每个外观参数另建价格档。未知字段若落在收费工具、候选数量、执行模式等高风险命名空间，也不能借“兼容扩展”绕过 A 类检查。

“保持原参数”不是平台保证支持。基础低风险功能可标记为上游校验；要对外宣称更强保障、跨不同协议适配或自动跨服务回退时，才需要相应的可靠能力证据。高级功能受限只影响该功能/该路由，不拖累已满足条件的基础调用。

### 1.2 配置负担矩阵

| 接入情景 | 平台自动承担 | 管理员要做的事 | 默认限制 |
| --- | --- | --- | --- |
| 已收录供应商及精确模型/协议版本 | 按已维护模板生成参数规则、能力来源和有效上限；复用现有输入 | 连接、凭据、模型映射、价格、开放范围；一般无需额外填写边界 | 只提供模板能支持或明确交上游校验的能力 |
| 自建/兼容 LLM，模板未命中 | 平台基础校验、既有业务策略、单候选及计费边界；复用定义与映射默认 | 无可信资料时，最多集中确认两个核心数：对外上下文上限、单次输出策略上限；已有值有效则不重填 | 这是平台提供的服务范围，不冒充已测定的上游极限；未知低风险参数上游校验 |
| 同模型新增一条部署 | 复用来源、模型与能力模板，显示差异 | 连接/价格照常维护；只有部署实际限值不同才覆盖 | 不因模型名相同就认定能力相同；可靠已知差异用于选路 |
| Embedding/Rerank | 模板维护批次、长度、维度/空间及截断规则 | 标准接入无逐参数维护；跨服务回退要有空间等价证据 | 缺等价证据可先固定单服务提供基础接口；不把所有基础接入都卡在回退验收 |
| 图像/ASR/TTS/视频 | 按类型和已知模型模板处理格式、规格和计量；ASR 不通用注入冲突格式 | 确认既有计费方式和开放规格；自定义模型只补与本次开放功能有关的关键缺口 | 不能计量/收费不可控的模式暂不开放；普通效果参数可由上游校验 |
| 业务方要求更严格限制 | 继承现有主体/用途/池策略并计算有效值 | 只在既有业务策略入口调整；不重复配置供应商能力 | 不改变上游能力，不把预占估算当生成上限 |
| 模板升级或供应商变化 | 生成影响差异、关联服务和建议动作；只使受影响证据失效 | 仅对影响公开承诺、开放能力或费用的变更处理一次 | 普通模板更新不要求逐服务、逐参数重新确认；有明确安全/费用问题则直接限制受影响功能 |

模板必须同时匹配供应商、模型/修订、协议与模式；只选择“OpenAI 兼容服务”不能推断某个精确模型能力。没有模板可以按受控基础路径接入，不要求管理员先制作一份模板。价格可复用已有合同配置，但不能由能力模板擅自确认或覆盖。

核心数值已有逻辑模型或业务策略时自动继承，服务只保存例外覆盖和来源，不再让管理员分别填写三份同义的“最大输出”。只有部署事实需要时才由技术维护者覆盖实际能力；业务限额仍走原策略入口。预占估算默认沿用，放到高级设置按需调整。

### 1.3 运营界面与验收负担上限

普通接入继续使用现有“登记模型 → 连接与价格 → 开放使用范围”，不新增“配置 50 项边界”的步骤。默认展示连接、模型、计价与简短的有效能力摘要，例如：“上下文：按模型继承；输出：受业务上限保护；高级参数：上游校验；还有 1 个计量问题需处理”。详细字段、原始来源、覆盖和诊断在现有详情/高级设置中按需展开；不新建参数规则编辑器或让运营填写校验 JSON。

只显示三类可操作信息：**阻止开放的关键问题、已经采用的默认值、可以稍后完善的提示**。不把所有 unknown/stale 状态堆成红色告警。只汇总对用户有影响且需要操作的重复异常；单次调用参数错误优先反馈调用者。

新增自动检查默认只读取不产生生成费用的元数据，不擅自扩大既有连接/实际验收的调用范围。已有可信模板或部署资料可作为规则来源，不要求探测最大窗口，也不要求基础生成把所有组合测一遍；需要实际收费验证的能力仍走既有实际验收入口与成本范围，不自动新增批量探测。无法由接口读取真实部署极限时明确说明，不能承诺“全部自动发现”。

首期同时验收保护与负担：

- 已收录的标准模型，边界治理新增必填项为 0；未收录的自定义 LLM，核心限制最多补两项，并复用已有值。
- 相同连接、模型和价格条件下，普通接入的阶段和必经人工操作不比现有流程增加；不逐项确认模板参数。
- 仅修改显示名称/说明不触发协议与费用重验；修改计价不要求重新填写能力；部署变化只复核相关能力。
- 不支持或未知的高级功能不阻断满足 A 类要求的基础功能；缺计量/费用保障只阻断相关收费模式。
- 用已知非法值与已有合法客户端请求共同验收：既要证明该拦的会拦，也要证明没有新增整类误拒绝。
- 模板维护有明确的平台侧责任人和版本，不能把维护工作转移给每个运营管理员。

## 2. 当前上下文和输出上限究竟如何处理

### 2.1 三个量分别负责什么

| 概念 | 当前来源 | 实际用途 | 是否限制上游生成 |
| --- | --- | --- | --- |
| 上下文长度 `contextTokens` | 逻辑模型定义，人工录入 | 准入时检查输入和输出能否容纳 | 间接；不是上游真实配置的自动镜像 |
| 请求输出上限 | Chat 的 `max_completion_tokens ?? max_tokens`；Responses 的 `max_output_tokens`；Messages 必填 `max_tokens` | 检查并转发明确的生成上限 | 是，前提是上游支持并遵守对应字段 |
| 管理策略输出上限 | 主体、用途、模型池、服务、服务模型映射等生效的 `UsageLimits` | 多层上限取最小值 | 是；客户端省略时也可能注入 |
| 目录“最大输出 Token” | `ModelDefinition.maxOutputTokens` | 运营维护的展示元数据 | **否，目前没有接入准入计算** |
| 预占输出估算 | `estimatedOutputTokens`；未设置默认 16,384 | 预占费用与准入估算 Token | **否** |

对 Chat，令 `I` 为平台估算输入，`C` 为配置的上下文，`P` 为各层输出策略上限的最小值（没有时视为无穷）：

```text
A = min(P, C - I)
显式输出上限 R：要求 R 为正整数且 R <= A，否则拒绝。
省略输出上限：有输出策略时转发 A；没有输出策略时保持省略。
预占输出估算 E = min(模型预占估算或 16384, 显式/策略输出上限或 A)。
```

省略时，`A` 约束本地估算，但在没有输出策略的情况下**不会自动作为 `max_tokens` 发给上游**。例如平台估算输入已经接近上下文，仍可能放行一个省略输出上限的请求，最终由上游默认行为决定是否拒绝或截短输出。

输入估算目前是通用 `cl100k_base` BPE，对结构化输入序列化后增加 25% 余量和 256 Token；每张已识别图片另加 8,192 Token。它覆盖工具等主要输入字段，避免把 Base64 当文本计算，但**不是当前上游的精确 tokenizer，也不是图片用量的普适上界**。[C01](../../packages/contracts/src/request.ts)、[C02](../../apps/control-plane/src/store/admission.ts)。

### 2.2 配置和上游对不上的情景矩阵

| 情景 | 当前行为 | 影响 | 建议策略 |
| --- | --- | --- | --- |
| 平台上下文填大，上游部署实际较小 | 按较大值检查；可能放行，由上游拒绝 | 请求消耗往返时间，用户只看到上游错误 | 服务映射记录部署实际上限，按服务过滤候选路由 |
| 平台上下文填小，上游实际较大 | 提前拒绝超出平台值的请求 | 可用能力被低估 | 区分“上游能力”与“平台公开上限”，展示实际生效来源 |
| 平台目录输出上限 1,024，客户端请求 4,096；其他策略及上下文允许 | 目录字段不参与准入，可以放行 | 展示承诺与实际准入不一致 | 统一目录承诺与执行契约；上游上限放在服务映射，不能只加展示字段 |
| 客户端显式输出超过生效策略或剩余上下文 | 拒绝，Chat 返回 400 和 `request_limit_exceeded`，带额度诊断 | 不自动压到较小值 | 保留拒绝语义；增加具体参数、服务边界来源及可选兼容路由诊断 |
| 客户端不传输出上限，没有管理输出策略 | 保持省略；预占使用独立估算 | 上游默认值未知时不能保证恰好适配剩余上下文 | 记录已知默认行为；临界请求优先计数复核。仅有估算不确定性时不一律封禁，符合平台费用/资源底线的原生请求可交上游校验 |
| 客户端不传输出上限，管理策略上限 512 | 注入不超过剩余上下文的策略上限 | 显式约束上游生成 | 保留，并在有效参数诊断中注明来源 |
| 同时传 `max_tokens` 和 `max_completion_tokens` | 后者优先用于准入；正常配置准入会生成路由上限，转发删除前者；未配置模拟/替身路径可能保留二者 | 当前采用优先级策略，不是统一冲突拒绝 | 建议入口统一拒绝双字段歧义，让行为独立于运行路径 |
| 同一个逻辑模型分别接 32K 和 128K 的服务 | 都读取同一个定义级 `contextTokens`，可配置不同映射输出策略，但没有独立服务上下文档案 | 不能准确识别哪个服务能承载长请求 | 先按能力筛选，再在兼容服务中负载分流 |
| 真实用量超过费用预占 | 有完整用量时尝试从原批次补足；不足或用量不完整则待核对 | 估算可能偏差；不跨批次随意补扣 | 保留账务边界；高风险应用可另选明确的费用硬预算模式，不能冒充 `max_tokens` |

普通 Chat 上游参数错误一般保留上游 HTTP 状态与错误体；协议适配路径会规范化错误，当前分类通常只到 `upstream_http_400` 等粒度。没有统一的上下文差异自动探测、输入压缩、输出降档或跨服务重发。仅对能够证明请求尚未发送的连接故障进行一次重试；不因为参数错误或已收到部分输出而重新生成。[C03](../../services/gateway-sim/src/server.ts)、[C04](../../packages/contracts/src/connection-failure.ts)。

## 3. LLM 参数边界矩阵

状态说明：“部分”表示有通用检查但没有完整服务契约；“透传”表示平台不保证该参数的上游支持、范围或实际效果。P0 为优先修补的核心契约、费用与资源问题，P1 为兼容能力完善，P2 为扩展优化。优先级描述平台实现次序，不表示运营必须手填或逐项验收；具体拦截强度以 1.1 的风险与证据分层为准。

| ID | 参数/边界 | 可能出现的不匹配 | 当前处理 | 建议处理 | 优先级 |
| --- | --- | --- | --- | --- | --- |
| L01 | `contextTokens`、输入上限、部署 `max_model_len` | 模型宣传窗口、实际部署长度与平台配置不同 | 部分：只用定义级 `contextTokens` | 服务级分别记录输入、输出、总窗口、模式和部署覆盖；取适用约束 | P0 |
| L02 | 三种 `max_*tokens` 字段 | 字段名、必填性、废弃字段、含不含推理 Token 不同 | 正整数检查；协议字段映射；DeepSeek Chat 特例 | 每个协议明确唯一字段、缺省/null/0 语义及别名冲突规则 | P0 |
| L03 | 独立最大输出长度 | 总窗口大，不代表能一次输出同样长度 | 目录字段不执行；可手动用映射输出策略限制 | 独立上游 `maxOutputTokens` 与业务上限参与准入 | P0 |
| L04 | tokenizer、chat template、特殊标记 | 中文、代码、工具 schema、模板开销与通用 BPE 不同 | 通用估算，存在余量但无精确保证 | 按服务适配计数；临界值优先复核。标注不确定性，不把通用估算当精确证据 | P1 |
| L05 | `reasoning_effort`、`reasoning.effort`、`thinking`、`thinking_budget` | 枚举、启用条件、预算范围随模型/模式变化 | Chat 与原生协议多为透传；适配路径拒绝部分高级能力 | 已知规则按协议/模式检查；普通未知枚举可原生上游校验，不猜测跨供应商等效 | P1 |
| L06 | 思考预算 × `max_tokens` × tools | 普通预算关系、交错思考例外、工具期间延续不同 | 未统一检查耦合关系 | 模板维护模型及模式约束；保留签名历史，不套统一关系；费用与总输出底线先执行 | P1 |
| L07 | `temperature`、`top_p` | 接受范围、开闭区间不同；推理模式可能拒绝、固定或忽略 | Chat/原生透传；适配路径有通用范围检查 | 确定非法值拦截；条件支持用模板；仅无效果且无费用/承诺影响时提示而不阻断 | P1 |
| L08 | `top_k`、`min_p`、penalties、`logit_bias` | 服务私有扩展、取值区间、token ID 词表不同 | 多数透传 | 通用 schema 加服务覆盖；token ID 必须对应实际 tokenizer | P1 |
| L09 | `min_tokens`、`min_new_tokens`、`ignore_eos` | 最小值高于最大值；强制生成延长开销 | 无统一组合检查 | 校验 `min <= max`；未定价/未接受的强制生成扩展拒绝 | P0 |
| L10 | `n`、`best_of`、候选数扩展 | 输出份数或内部采样量放大费用与容量 | Chat 已拒绝非 `n=1`；其他放大参数无统一契约 | 保留单份输出；显式拒绝未建模的候选/采样放大参数 | P0 |
| L11 | `stop`、`stop_sequences`、`stop_token_ids` | 条数、每条字节数、模型支持和停止原因不同 | Chat 透传；Messages 适配拒绝非空 stop sequences | 校验数量/字节/支持性；按协议准确保留 stop reason | P1 |
| L12 | roles、连续消息、system/developer | 角色及顺序限制；模板语义差异 | Chat 部分结构检查；DeepSeek 主机特例转换 developer→system | 用服务协议规则；转换必须有等效依据与原文审计，不能只看模型名字 | P1 |
| L13 | `tools`、`tool_choice`、`parallel_tool_calls` | 工具数、命名、schema 子集、强制工具与推理模式组合受限 | 适配路径有较多结构检查；Chat/原生缺完整服务校验 | 已知组合用模板；客户端工具未知细节可原生上游校验，收费服务端工具受 A 类约束 | P1 |
| L14 | `response_format`、`json_schema`、`strict`、grammar | 支持 JSON 不代表支持严格 schema；schema 深度/枚举/关键字不同 | Chat/原生透传；Responses 适配拒绝结构化输出 | 已知子集用模板；原生未知可交上游校验；严格输出要求不自动退成普通文本 | P1 |
| L15 | `seed`、确定性、`system_fingerprint` | 接受 seed 不代表跨版本、跨服务输出可复现 | 透传 | 声明尽力确定性；需要复现时固定服务、模型快照及参数版本 | P2 |
| L16 | `logprobs`、`top_logprobs`、`prompt_logprobs` | 最大数量、模型支持、响应体爆炸 | 透传；非流式文本响应有 16 MiB 限制 | 能力与响应预算联合校验；限制大词表输出扩展 | P1 |
| L17 | `stream`、`stream_options.include_usage` | 服务不支持该选项、usage 在不同帧、流中断无最终量 | 非原生 Chat 流强制补 include_usage；已有多协议 usage 处理 | 验证“流 + 最终量”能力；不支持时明确限制，不能用本地估算冒充结算量 | P0 |
| L18 | 图片理解：数量、字节、像素、MIME、`detail` | 每图与整批限制不同；图片 Token 随模型/分辨率变化 | 检查 Chat 图片块基本结构；每图暂估 8,192；详细校验交上游 | 平台资源上限先执行；具体规格逐步用模板，未知可上游校验，不额外抓取远程 URL | P1 |
| L19 | 原生 document/file、PDF 页数、音视频块 | 未知块不一定能估算；解码页数比文件字节更关键 | 原生协议允许部分上游自有块；音视频计量边界会拒绝已知类型 | 只开放可表达、可计量且验收过的块；文件引用绑定服务与有效期 | P1 |
| L20 | `previous_response_id`、conversation、store、background、truncation | 状态归属上游，换路由后引用失效；自动截断丢语义 | 状态式字段及部分后台能力明确拒绝；原生/适配对 truncation 检查不完全一致 | 保持无状态边界；若支持需固定归属、单列生命周期及删除策略 | P1 |
| L21 | `service_tier`、web search、server tools、缓存控制 | 可以改变价格、计费项或缓存写入成本 | 原生有 server-tool 拦截，但 Responses `web_search` 是兼容例外；费用不保证完整 | 没有价格/用量证据的附加收费项禁止上线；按条件费率结算 | P0 |
| L22 | 版本头、beta、私有参数 | 同字段随 API 版本变义；上游接受却忽略 | Messages 要版本头；beta 仅原生转发，适配拒绝 | 能力档案绑定头/版本/模式；升级失效重验，不用基础连通通过替代参数验收 | P1 |

官方差异例证：OpenAI 的 `max_completion_tokens` 包含可见输出和推理 Token，`max_tokens` 并不适用于所有推理模型；其 Chat stop 通常最多 4 条，DeepSeek 当前文档允许最多 16 条且按 UTF-8 字节限制。DeepSeek 的采样参数在部分思考模式会忽略或固定；硅基流动另有 `enable_thinking`、`thinking_budget` 等条件字段。它们共同说明“OpenAI 兼容”只描述部分协议形状，不能证明参数完全相同。[OpenAI Chat](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)、[DeepSeek Chat](https://api-docs.deepseek.com/api/create-chat-completion/)、[硅基流动 Chat](https://docs.siliconflow.cn/docs/api/chat-completions-post)。

Claude 普通手动思考预算要求至少 1,024 且小于 `max_tokens`，手动交错思考存在例外；新版模型对手动/自适应模式也有不同支持条件，必须保留模式维度。[Claude extended thinking](https://platform.claude.com/docs/en/build-with-claude/extended-thinking)。

## 4. 其他模型类型的参数边界矩阵

目前模型类型为 `chat / embeddings / rerank / image / asr / tts / video`。下面覆盖其输入、生成、输出兼容与计费边界；未做过真实供应商调用的组合不视为已验收。

| ID | 类型 | 参数/边界 | 当前处理与风险 | 建议策略 | 优先级 |
| --- | --- | --- | --- | --- | --- |
| M01 | Embedding | 单条最大 Token | 已区分最长单条和整批 Token，按最长单条检查上下文；字符串仍为通用估算 | 独立 `maxTokensPerInput`，服务 tokenizer 计数 | P0 |
| M02 | Embedding | 整批 Token、条目数、空输入 | 没有服务级整批/条数限制；空字符串能过本地解析 | 独立 `maxBatchTokens/maxItems`；明确空白、空数组、token-array 规则 | P0 |
| M03 | Embedding | `dimensions`、编码、归一化、稀疏/稠密 | 多数透传；响应仅做基础结构检查 | 校验可选维度、类型、有限数值、数量和 index，禁止静默填充/降维 | P0 |
| M04 | Embedding | `task/input_type`、query/document 指令、模型修订 | 透传或当前输入结构无法表达多模态；同维度也不代表同向量空间 | 向量空间标识绑定模型/修订/维度/任务/归一化；回退服务须保证语义兼容 | P0 |
| M05 | Embedding | truncate、late chunking、多模态输入 | 截断丢尾文；图片/视频/文件不能套文本长度 | 默认不截断；已开放模式才受理；自动分批另做显式功能，保序且有部分失败语义 | P1 |
| M06 | Rerank | query 长度、每篇/每对窗口 | 当前把 query 与所有 documents 合并估算，套统一上下文；可能误拒绝 | 模型专用计数 `query + document + template`，另设 query 单独上限 | P0 |
| M07 | Rerank | 文档数、总工作量、分块数 | 无服务级档案；长文可能被上游截断/分块，费用单位不同 | 分开记录文档数、逐篇长度、总 Token/搜索单位；不把 1,000 条推荐当通用硬上限 | P0 |
| M08 | Rerank | `top_n/top_k`、return_documents、rank_fields | 基础 query/documents 检查后透传；非法 `top_n=0` 能过解析 | 校验返回数、结构化文档和模型支持；返回 index 必须对应原文，score 语义不跨模型硬比较 | P1 |
| M09 | Rerank | `max_tokens_per_doc`、truncate | 平台未表达上游自动截断行为 | 模板公开已知截断规则；要求完整文档时执行相应承诺，普通请求不增加手工验收门槛 | P1 |
| M10 | 图像生成 | prompt 字符/字节/Token、负向提示 | 只要求 prompt 非空并估算文本 | 按模型分别计数；负向提示、权重语法按能力开放 | P1 |
| M11 | 图像生成 | `n/batch_size`、候选数 | `n` 经 Number 转换限制 1–10，其他放大字段未统一建模；上游常有更小限制 | 服务上限与业务上限共同限制；拒绝未计量的候选扩展 | P0 |
| M12 | 图像生成 | size、宽高、步长、像素总量、ratio、quality | 基本透传；非法 size 也能通过本地解析 | 枚举或宽高/整除/比例联合约束，价格按有效规格选择 | P0 |
| M13 | 图像生成 | steps、guidance/CFG、sampler、seed | 服务私有字段；可能忽略或增加推理成本 | 模型专用范围/条件，未知收费扩展拒绝 | P1 |
| M14 | 图像生成 | output_format、background、压缩、URL/Base64、stream | 多数透传；统一拒绝该端点 `stream=true`；同步媒体响应最多 32 MiB | 校验透明度×格式、响应大小和交付能力；不把已支持生成等同支持编辑/蒙版 | P0 |
| M15 | 图像编辑/参考图 | 输入图数量、大小、蒙版对齐、alpha、参考权重 | 当前公共入口以图片生成为主，没有独立编辑/蒙版契约 | 独立任务模式及验收，未支持的请求明确拒绝 | P1 |
| M16 | ASR | 容器、编码、采样率、声道、字节、实际时长 | 只要求 multipart 非空文件；总请求体 20 MiB；没有可信音频时长检查 | 检查实际格式/可解码元数据；分别限制字节和时长；媒体时长不能由文本 Token 替代 | P0 |
| M17 | ASR | model × response_format × timestamps | 未传格式时统一补 `verbose_json`；对只支持 json 的模型会制造不兼容 | 移除通用猜测，按已验收服务档案选择默认格式；时间戳能力和计量证据一起校验 | P0 |
| M18 | ASR | language、prompt、temperature、chunking、diarization | 大部分字段透传；重复 form key 在 body 投影中可能丢失，但转发 FormData 保留 | 解析为明确标量/数组；校验说话人数、参考音频、长音频分块与参数组合 | P1 |
| M19 | ASR | streaming 与实时音频 | 媒体入口统一拒绝 `stream=true`；不等于支持 WebSocket 实时会话 | 清晰声明批量转写能力；实时模型需另有帧、会话和背压契约 | P1 |
| M20 | TTS | input/instructions 长度和计数字符单位 | 只检查 input/voice 非空；以 Unicode 码点数预估字符计量；无模型长度上限 | 按服务定义字符/字节/Token限制及收费字符规则，检查输入与指令总量 | P0 |
| M21 | TTS | voice、语言、speed、style、采样率、输出编码 | 多数透传；未知 voice、负 speed 能过本地解析 | 按模型及音色校验支持集合和组合；二进制 MIME 与编码必须匹配 | P1 |
| M22 | TTS | 克隆参考、SSML、流式片段、长文切分 | 当前无完整对应契约，不能以基础 speech 成功代表支持 | 单独模式；文本切分必须用户可预期，合成费用及失败结果可追踪 | P1 |
| M23 | 视频 | seconds/duration/frames/fps、特殊自动值 | 通用校验仅 `0 < 时长 <= 3600`，允许小数；拒绝 -1；多个字段冲突未统一处理 | 服务及任务模式专用类型、范围、枚举、互斥；自动值与“未知最终时长”分开 | P0 |
| M24 | 视频 | resolution、ratio、size、生成音频、批量数 | 基础透传；没有组合能力或规格价格档案 | 联合校验时长×分辨率×音频×份数，并选择对应计价规则 | P0 |
| M25 | 视频 | 文生/图生/参考/编辑、content 引用 | 火山转发会把 prompt 改成 text content；没有完整保留复杂素材任务的适配契约 | 区分任务模式，不把原生复杂任务压成单段文本；素材类型/数量/有效期分别约束 | P0 |
| M26 | 视频 | 异步提交、轮询、超时、取消、结果过期 | 已有持久化任务、回执恢复、取消能力配置和用量待核对 | 保留不盲目重提；区分取消申请和已取消；按档案检查任务 TTL/结果 URL/服务归属 | P0 |
| M27 | 全部按量模型 | 单位、精度、maxUnits、真实用量字段 | `meter.maxUnits` 约束准入估算量；不是全部生成规格的硬限制；缺实际量则待核对 | 上限校验、预占单位、账务单位分开；统一记录单位和换算依据，禁止用估算补“实际量” | P0 |
| M28 | 全部模型 | 响应长度/形状/实际规格 | 多模态响应验证较浅；空数组、维度/索引/实际规格可能未完整核对 | 响应也执行契约；记录长度截断、空结果、部分结果；不把 HTTP 200 当完整任务成功 | P1 |

具体差异的官方依据：

- OpenAI Embedding 文档同时列单条输入 Token、批次条数及整批总 Token 限制（当前示例为 8,192、2,048、300,000）；这些是不同维度，不能用一个 context 字段替代。[Embedding API](https://developers.openai.com/api/reference/resources/embeddings/methods/create)。
- Jina 提供不同向量维度、编码与多模态/任务能力；跨服务回退前必须验证向量空间，不能只比较维度。[Jina Embeddings](https://jina.ai/embeddings/)。
- Cohere Rerank 对长文默认按 `max_tokens_per_doc` 截断，当前默认 4,096；文档数 1,000 是性能建议，不应直接当作所有模型统一硬上限。[Cohere Rerank](https://docs.cohere.com/reference/rerank)。
- OpenAI 图像 API 有模型专用尺寸规则，透明背景还依赖 PNG/WebP 等输出格式，说明规格必须做组合检查。[Image API](https://developers.openai.com/api/reference/resources/images/methods/generate)。
- OpenAI 转写模型的输出格式集合不同，部分模型只支持 json；时间戳、说话人分离与分块也有条件。当前平台默认 verbose_json 的策略存在明确兼容风险。[Transcriptions API](https://developers.openai.com/api/reference/resources/audio/subresources/transcriptions/methods/create)。
- OpenAI speech 当前 input 最长 4,096 字符，voice、instructions、速度和编码支持与模型有关。[Speech API](https://developers.openai.com/api/reference/resources/audio/subresources/speech/methods/create)。
- OpenAI 视频接口当前 seconds 为 4/8/12 的字符串枚举；xAI 生成接口使用 duration，生成与编辑任务规则不同；火山还有 frames、duration=-1 及模型/任务特定规则。不能共用一个连续 0–3600 秒区间。[OpenAI Video](https://developers.openai.com/api/reference/resources/videos/methods/create)、[xAI Video](https://docs.x.ai/developers/model-capabilities/video/generation)、[火山创建视频任务](https://docs.volcengine.com/docs/ark/create-video-generation-task-api?lang=zh)。

尚未作为独立模型类型接入的 OCR/文档解析、分类/审核、目标检测、实时语音，也有页数/DPI/框坐标/标签集合/阈值/音频帧和会话时长等边界。后续新增应建立对应任务契约；当前不能声称这些独立接口已被上述七种类型完整覆盖。

## 5. 统一处理决策矩阵

下表是目标行为，不代表已经实现；它与 1.1 的分层一起使用，不以“未知即失败”作为统一默认策略。

| 条件 | 保存/开放服务时 | 用户请求时 | 是否允许自动调整 |
| --- | --- | --- | --- |
| 已知硬上限超出 | 拒绝矛盾配置，展示来源；平台主动设小上限可接受 | 兼容服务中路由；没有则返回具体边界错误 | 不静默压低用户显式值 |
| 已知参数不支持 | 不能对外宣称该能力，不阻止独立的基础功能开放 | 对相关请求返回 `unsupported_parameter`，或选兼容服务 | 不静默删除 |
| 字段单独合法，组合不合法 | 验收规则覆盖依赖组合 | `parameter_conflict`，列出冲突字段 | 不猜测用户优先级 |
| 上游会忽略/固定参数 | 模板记录 ignored/conditional，无需运营逐项维护 | 无费用/资源/承诺影响时提示并转发；影响明确承诺时拒绝相关请求 | 不把接受当生效，不偷偷重写参数 |
| 客户端省略参数 | 记录已确认的默认值或默认行为 | 继承已发布默认；上游默认可验证时保持省略 | 允许注入明确发布的业务上限，需标记来源 |
| null、0、空字符串、未知枚举 | 分别建模，不能用真值判断混为缺省 | 按字段契约接受/拒绝 | 不通用 Number 强制转换，不把 0 自动当未传 |
| 两个同义字段同时出现 | 定义唯一规范字段 | 统一拒绝歧义；兼容策略若允许相等值须显式定义 | 只有经证明等效的字段转换可自动做 |
| 参数影响收费但没有价格/量纲 | 禁止宣称可结算开放 | `unpriced_capability` | 不带着未知费用试发再补账 |
| 低风险兼容能力未知/仅证据过期 | 记录来源与状态，不显示已实测，不一律禁止基础开放 | 满足平台底线、无已知冲突且原生可表达时交上游校验；不依赖未知能力跨协议转换/回退 | 不静默删除参数，不用用户请求反复试错 |
| 收费/资源/状态归属能力未知 | 只限制无法守住底线的功能；其余基础能力独立开放 | 拒绝相关请求；升级验证只针对缺口 | 不因追求兼容绕过平台底线 |
| 仅通用 Token 估算接近/超过窗口 | 展示计数方法与不确定性，避免让运营配置误差系数 | 优先使用可信计数；只有不精确估算时，满足平台底线的原生请求可由上游最终判定 | 不当作已证实超出上游硬上限，不为了继续调用偷偷截断 |
| 输入超过窗口/文档限制 | 标注最大值和长度单位 | `context_length_exceeded` 或 `input_limit_exceeded` | 不自动删消息、摘要、截文；应用显式启用时另行处理 |
| HTTP 成功但输出被长度限制 | 验收确认停止原因与 usage | 保留 length/incomplete、部分工具 JSON 和实际费用 | 不自动续写或重跑 |
| 上游 429、5xx、连接/流中断 | 记录能力与运行健康为不同维度 | 429 单列重试提示；已发请求按证据结算，未知量待核对 | 仅可证明未发送时安全重试；其余不盲目生成 |

错误响应建议包含：稳定 `code`、公开字段路径 `param`、收到的值、已知的公开允许范围/枚举、限制来源、计量单位、`requestId`、能力档案版本；没有可靠上限就保留未知，不能编造范围。内部保留 serviceId/upstreamModel/原始错误及 trace，外部根据权限展示。原生协议的错误包络保持对应协议形状。标量越界一般 400，媒体过大 413，速率限制 429，必要安全/计量契约未就绪才用 503；业务授权/额度错误保留现有独立语义。

## 6. 最小可落地设计

### 6.1 放在哪一层

复用现有 `ModelDefinition`、`ServiceModel`、`protocolCapabilities` 和配置版本，不再建立另一套模型注册表。

| 层 | 应负责的内容 | 约束 |
| --- | --- | --- |
| 逻辑模型定义 | 对用户发布的稳定能力、公开上下文/输出承诺、描述 | 区分“宣称”与“已验证”；展示字段不能冒充执行限制 |
| 服务模型映射 | 模板引用、上游模型修订、必要的部署例外覆盖 | 按 service + mapping + upstream model/revision + protocol + mode + configVersion 解析有效能力；不复制整份模板让运营维护 |
| 池/主体/用途策略 | 更严格的业务上限、允许功能和费用策略 | 不得放大上游能力；允许不同用途采用不同上限 |
| 路由与准入 | 参数规范化、兼容候选过滤、选路、预占 | 能力过滤先于排序；选定服务后确认生效参数并冻结 |
| 数据面适配 | 已验证的字段/包络等效转换、转发、结果校验 | 不推断或伪造能力；不能改参数后复用旧费用/路由快照 |

平台内部规则可以表达数值上下界及开闭区间、枚举、长度单位、必填/nullable/缺省语义、互斥与条件、支持状态、计数方式/精度、计量和规格价格、来源与证据版本；这些是表达能力，不是每个服务的必填字段。模板可以渐进覆盖，未知兼容项可以留空，实际证据才有验证时间。`supported / unsupported / unknown / conditional / ignored` 主要用于内部选路和诊断，运营只看到有效能力摘要及需要处理的例外。

首期采用共享基础校验与适配器内的少量已知规则，加模板引用和服务覆盖即可，不引入通用规则脚本、可编程表达式引擎或另一个运营规则编辑器。模型特有的复杂组合可留在对应适配器；只有重复需求得到验证后再抽共性。平台研发/适配维护者维护技术模板，供应商或部署维护者提供实际部署差异，运营/财务维护连接、开放范围与价格，应用开发者维护具体生成参数及显式截断/分批策略。[现有表单](../../apps/web/src/editors.ts) 已有上下文、资料输出、预占估算和多层策略入口，改造应合并这些概念的展示与来源，而不是叠加更多同义字段。

上下文档案应区分 `maxInputTokens / maxOutputTokens / maxContextTokens / contextAccounting`，而不是默认所有模型都遵循一个窗口公式。对采用合并输入输出窗口的模型，规范化后的总输出预算应已包含其思考 Token，再计算 `I + O <= C`，避免重复加思考量。缓存命中不意味着对应文本不占上下文。[Claude context windows](https://platform.claude.com/docs/en/build-with-claude/context-windows)。

自建服务的部署配置是必要证据：vLLM 可配置 `max_model_len` 和 generation config，不能仅按模型卡或模型名称推断在线能力。[vLLM ModelConfig](https://docs.vllm.ai/en/latest/api/vllm/config/model/)。

### 6.2 请求顺序

```text
解析公共请求，校验类型/别名冲突/平台明确不支持的能力
  → 找出授权范围内服务候选
  → 按已知可靠规则和平台底线过滤候选；未知低风险项保留为上游校验
  → 有可靠计数能力且需要时做临界复核，避免逐请求增加一次外部依赖
  → 在兼容候选中按现有策略排序
  → 按实际候选的有效规格报价/检查业务限额/预占
  → 冻结 route + effective parameters + capability version + price
  → 执行该服务适配并发送
  → 保留结束原因，核验响应与权威用量，结算或待核对
```

计数优先使用适配服务的本地 tokenizer；临界且有适配能力时才使用官方计数接口，不把每次生成强制变成“计数调用 + 生成调用”。官方接口自身也可能是估算，并有不支持的块类型，不能承诺全类型精确。若计数不可用，按 1.1 的风险分类决定回退，不使全服务因可选计数依赖故障停用。远程 URL 不为此在网关任意抓取，保持当前受控媒体边界。用量结算仍以权威返回或经核对的证据为准。[Claude token counting](https://platform.claude.com/docs/en/build-with-claude/token-counting)。

参数过滤放到准入前需补充现有授权请求：今天控制面主要收到估算 Token、输出上限及 fingerprint，并没有全部参数特征，无法据此验证完整组合。应由共享规范化/校验模块产出有界的请求能力需求（例如结构化输出、工具、模式、尺寸、时长、输入类型），避免为选路复制全文 prompt；复杂 schema 在受控数据面校验，结果与原始请求哈希绑定。报价、路由模拟和真实请求应调用相同规则。

池可展示“共同保障能力”和“至少一个服务可提供的扩展能力”两种投影；实际请求仍逐服务过滤，不能简单把所有服务能力取并集后随机转发，也不必为一个低配服务把全池长期压到最低能力。Embedding 回退另需向量空间等价约束。

### 6.3 验收与运行证据

连接检查通过只能证明目录/协议连通；基础生成成功只能证明该请求组合成功，不能证明最大上下文、输出上限或所有参数。当前已有基础、stream、tools、实际模态探针，可以扩展并复用证据链。[C05](../../apps/control-plane/src/platform/verification.ts)、[C06](../../apps/control-plane/src/platform/model-acceptance.ts)。

建议把证据拆为 `declared / configured / verified / observed`。`observed` 失败作为漂移告警线索，不自动改写上限；一次最大长度失败也不能证明精确边界，可能受套餐、速率、负载或模式影响。验证按功能关联失效：修改显示名称/说明不失效；修改部署或协议规则使相关证据 stale；修改价格只复核计费证据。stale 影响验证标签与相关保障，不自动禁用无关基础能力。旧请求继续使用已冻结版本。

模板更新提供差异及影响说明，现有服务保留所引用版本，不因模板新增一个字段就要求全部运营重新确认。已确认的安全/费用问题或硬不兼容要及时限制受影响请求并通知责任人，不能以旧模板为由继续宣称能力。补充规则与复核过程由平台维护者承担，运营只处理真实部署例外或业务决策。

运行指标复用现有调用与诊断能力，先补本地拒绝/误拒绝、上游参数 4xx 和最终 usage 缺失；计数偏差、规格不符、能力漂移按实际需要扩展，不要求首期新增完整监控产品。单个调用错误反馈开发者；重复且需要管理员操作的异常再聚合通知。参数 4xx 应单独分类，避免与模型服务健康故障混算后触发不必要的冷却。当前路由观察会把部分 `upstream_error` 计入连续失败，需要在实现阶段细分。[C07](../../apps/control-plane/src/store/pool-routing.ts)。

| 运行与恢复 | 400/413/429/5xx；首字节/空闲/总超时；断流无 usage；版本升级 | 参数错误与健康故障分开；账务与冻结版本一致 |
