# 企业 AI 资源运营平台：通俗介绍

面向对象：懂 AI 基本概念（模型、Token、API Key），但不需要看代码的商务、解决方案和客户同学。
一句话版本：**让企业像管理"办公用品领用"一样管理 AI 使用——谁能用、能用多少、花了多少、出了问题找谁。**

---

## 1. 先说清楚它解决什么

企业用 AI 的真实难点通常不是"找不到模型"，而是这几件事：

| 常见现状 | 后果 |
| --- | --- |
| 各团队自己去各家厂商注册账号、绑卡 | 费用散落在十几张账单里，没人说得清哪个部门花了多少 |
| API Key 在群里传来传去 | 谁在用、用了多少、离职后还能不能用，都无从查证 |
| 只有"总额度"，没有"谁多少" | 一个项目把预算用光，其他人当天无法工作 |
| 出问题时只看到"报错了" | 分不清是余额不足、模型故障、还是网络超时 |

平台把这些收回到一处：**统一入口、统一额度、统一账本、统一证据。**

打个比方，它同时扮演三个角色：

- 交换机：所有 AI 请求从一处进出，转给对应的模型厂商；
- 财务：每次调用先冻结额度、结束后按实际用量结算，账目对得上；
- 审计：每次调用留下一条可追溯记录，但**不保存对话正文**。

---

## 2. 四个核心概念（看懂这四个就够）

### 额度主体：钱挂在"谁"身上

平台里有四种独立的"钱包"，彼此不互相补扣：

1. **个人额度**——发给某个员工，供他日常使用；
2. **项目额度**——发给一个项目，由项目经理再分给成员；
3. **应用额度**——发给一个系统/服务（例如客服机器人），不依赖某个人是否在职；
4. **组织范围发放**——一次给某部门/某类人发一批，但不等于"以后新来的人也自动有"。

### 开通方案：把"能用的模型 + 给多少钱 + 到哪天"打包

方案里写清楚：允许用哪些模型、每人多少钱、一次性还是每月发、什么时候失效。
运营选人 + 选方案 → 预览名单和总金额 → 确认执行。
同一份方案不会因为重复点击发两次钱。

### 密钥：只是"进门凭证"，本身不带钱

- 完整密钥只在签发那一刻显示一次，之后只保存不可逆摘要，平台自己也看不到明文；
- 一把密钥绑定一个用途，多把密钥共享同一份余额，**多发几把也不能绕过总额度**；
- 员工想直接用网页里的"在线使用"，可以不创建任何密钥。

### 用途隔离：日常额度和项目额度不互相兜底

员工拿个人额度做项目的事，余额不够时会**报"额度不足"，不会偷偷从项目预算里扣**。这是刻意的设计——否则预算永远对不上。

## 3. 一个具体场景走一遍

> 员工小林要用 AI 处理工单。

1. **运营**在"为人员开通"里选中林工，给他一个"办公体验方案"（含 2 个模型、每月 20 元）。预览显示影响人数、金额、到期日，确认后生效。
2. **林工**登录后看到"我的额度"和可用模型。他直接在"在线使用"里提问——不需要找服务地址、不配密钥。
3. 发送前页面会提示这次调用的**费用上限**；结束后按实际 Token 结算，并且给出一条**请求编号**。
4. **运营**在"用量驾驶舱"看到林工本月花了多少、主要用哪个模型、有没有异常；点进名字直接跳到他的调用记录，再点进单条看到结果、Token、价格依据、扣的是哪笔额度。
5. 如果某次调用**上游没返回完整用量**，这条不会显示成"已扣费"，而是进入**待核对**：由人来判断是确认计费还是释放预占。宁可显示"待处理"，也不假装账已平。

整个链条里，运营看到的和员工看到的是**同一条记录**，不会各说各话。

## 4. 不同角色分别看到什么

| 角色 | 主要界面 | 他们关心的事 |
| --- | --- | --- |
| 运营 | 运营工作台、用量驾驶舱、为人员开通、模型配置、密钥与接入、运行监控 | 谁能用、花了多少、异常谁处理、要不要扩模型 |
| 项目经理 | 项目用量、项目详情、申请与审批 | 我这组人还剩多少、谁提的额度申请要批 |
| 普通员工 | 开始使用、我的额度、在线使用、调用记录 | 我能不能用、还剩多少、这次花了多少 |
| 系统负责人/开发 | 应用、密钥与接入、接入指引 | 服务端怎么接、密钥什么时候到期、怎么轮换 |
| 安全/合规 | 安全围栏、调用记录、操作记录 | 有没有敏感内容外发、谁改过配置 |

部署形态是**一个网页 + 一套后端**，运营和员工在同一个入口，按身份看到不同空间。界面支持多套视觉风格一键切换（同一套业务规则，只是外观不同），方便做评审和演示。

## 5. 五组能力点（客户常问的部分）

**① 模型接入与开放**
支持三类主流接口格式：Chat Completions、Responses、Messages。同一个模型能原生支持就直接透传，不支持就自动转换，业务侧只填一个地址。模型目录里能看到每个来源的**配置价格和开放范围**；只有"连接验证通过 + 价格已确认"的服务才能开放给同事使用。

**② 准入与限流**
请求进来先校验身份、用途、模型权限、剩余额度，再决定转发。重复提交不会重复扣钱（幂等）；同一请求被重放会被识别并拒绝，避免钱花了两次。

**③ 计量与对账**
计费精确到**微元**（六位小数）；价格以"下单那一刻的快照"为准，事后调价不影响历史账。缓存命中单独记录，不重复计入总输入的金额。

**④ 观测与告警**
明确每个指标的**分母**：客户端取消不算"模型故障"，权限不足和余额不足也不算。无流量、样本太少、采集失败都会显式标注"证据不足"，不会因为没数据就自动宣布"已恢复"。告警可以配窗口、最小样本、连续触发次数，并区分"我知道了这个故障"和"故障真的恢复了"。

**⑤ 安全围栏（输入检查）**
可配置"仅记录"或"拦截"。命中拦截时请求**不外发、不预占、不扣费**，只留一条不含原文的安全事件。适合先观察一段时间，再切到拦截。

## 6. 输出/接入方式

- **网页直接用**：不需要密钥，适合办公场景。
- **任意 OpenAI 兼容工具**：填平台地址 + 一把平台签发的 Key 即可。
- **编程/桌面客户端**：支持 Anthropic Messages 协议的客户端也能直连；平台提供一条"网页签发 Key → 一键导入本机客户端"的路径（Windows 首次需运行一个轻量安装脚本）。
- **服务端系统**：用"应用"身份接入，额度独立于人员变动。

## 7. 工程设计上值得对外讲的几条原则

1. **权限和钱分开记**：模型权限来自"授予的权益"，扣款来自"有效的额度批次"，两者必须同时成立才能调用。往账户里加钱**不会**自动放开新模型。
2. **默认不存正文**：日志只留元数据（谁、何时、用了哪个模型、多少 Token、多少钱、结果如何）。监管或客诉需要时，靠请求编号而不是靠翻聊天记录。
3. **只可信的计价**：价格由平台配置并留快照，不接受请求方自己声明的价格。
4. **失败要看得见**：中断、超时、用量缺失都会显式进入"待核对"，而不是悄悄记成 0 元。
5. **可替换的数据面**：转发层（当前是 Higress）可以替换，账务和权限留在自家后端，不把核心资产绑死在某个组件上。

已具备并做过可重复验证的部分：人员开通与自动开通、项目与应用独立额度、统一审批、密钥生命周期、在线使用与多协议接入、调用追溯、待核对处理、监控告警、安全围栏、模型目录、备份恢复与容器化交付。

**尚未在客户环境验证**（需按项目立项验收）：企业 SSO/通讯录同步、真实内网的 HTTPS 与浏览器证书、生产规模容量与压力表现、外部通知渠道（邮件/IM）送达。当前容量与性能数据来自本地模型替身和受限的真实模型调用，**不能当作生产容量承诺**。

也就是说：核心业务闭环已经跑通并有自动化证据，但"客户现场交付"这一步需要单独的验证与确认，请不要用本地演示结果替代。

## 9. 客户高频问题

**Q：这跟直接用厂商 API 有什么区别？**
厂商 API 只回答"模型能不能算"。平台回答"公司里谁能算、算多少、算完钱从哪里扣、出事谁处理"。两者是叠加关系——平台后面接的仍然是各家厂商。

**Q：会不会把我们和某家厂商绑死？**
模型、服务、协议都是配置项。同一批人可以在不同模型间切换，也可以接自建/私有化模型，业务代码不用改。

**Q：运营能看我的对话内容吗？**
默认不能，也不保存正文。运营看得到的是调用元数据（模型、Token、费用、结果状态）。安全围栏也只保存"命中了哪条规则"，不保存命中文本。

**Q：员工额度用超了会怎样？**
调用前就会被拒绝，并明确提示"额度不足"。不会静默透支，也不会自动从别的用途补扣。

**Q：重复点击会不会发两次钱？**
不会。授权、结算、发放、审批执行都是幂等的；预览会显示"跳过/排除"的数量和原因。

**Q：能按部门/职级自动开通吗？**
可以。规则由"组织 + 人员类别 + 业务标签"这类简单条件组成（AND 关系），不写脚本。启用时默认只影响以后新增或属性变化的人，存量人员需要显式"预览并应用"。
