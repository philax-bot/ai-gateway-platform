# 企业内部 AI 资源运营平台：项目与模型资源修订 v1.2

> 后续修订：[企业运营能力 v1.3](token-operations-product-concept-v1.3.md)。审批统一进入审批中心，企业菜单及自动开通、密钥、监控以 v1.3 为准；本文项目额度与模型资源规则继续适用。

日期：2026-10-15。当前范围依据：本修订与 [首版易用性概设 v1.1](token-operations-product-concept-v1.1.md) 合并阅读。项目生命周期、模型资源组织、限流入口如有冲突，以本修订为准；其余首版边界延续 v1.1。

## 1. 这次修订的目标

简化配置不能删除运营真正需要的对象。本版恢复可复用的模型目录、模型服务和模型池，并补齐项目从申请到可使用的过程。通过默认值、关联对象就地创建、返回后自动选中减少操作，而非将不同对象合为一个不可复用的配置。

用户明确要求：运营创建项目并指定经理；第一版普通员工可以创建项目申请，运营审批后可用；运营直接给项目发额度并设有效期；经理申请项目额度；经理与运营均可向成员分配项目额度；保留供应商、模型定义、按用途划分模型池。

下文的具体命名、限流组织方式和额度到期处理为推荐设计，可随原型评审调整。

## 2. 项目创建与职责

| 发起人 | 入口与动作 | 生效方式 |
| --- | --- | --- |
| 运营管理员 | 项目列表 → 创建项目 → 指定经理 | 直接生效，不要求自己审批自己 |
| 普通员工 | 我的项目 → 申请创建项目 → 填写用途、建议经理 | 运营审批，并确认最终经理后生效 |
| 项目经理 | 项目详情 → 申请项目额度 | 运营批准后，额度进入项目 |
| 项目成员 | 我的额度 / 项目详情 → 申请个人项目额度 | 经理批准；经理本人向自己申请时转运营 |

项目状态：待审批、已驳回、已启用。待审批和驳回项目可查看申请记录，但不能发放、分配、签发可用项目凭证或调用。驳回后可修改并重新提交。审批通过并不意味着自动获得额度；界面提示下一步由运营发放或经理申请。

第一版普通员工均可申请创建。后续收紧到下级部门特定角色时，调整创建申请权限；不改变项目本身的生命周期。

经理是一项可叠加职责，申请人不必自动成为经理。运营确认其他经理时，原申请人仍保留必要的申请可见性与成员身份。

## 3. 项目额度：先到项目，再分到人

运营在项目详情点击“发放额度”，填写金额与过期日期。一次发放形成一批额度；后续追加保留不同批次、不同有效期，不能用修改一个总余额的方式覆盖历史。

经理点击“申请项目额度”，填写金额、使用说明和期望有效期。运营审批时确认金额和最终有效期，可按需要调整；通过后形成一批项目额度。项目经理不能批准自己的项目总额度申请。

运营和经理都可以在项目详情给成员分配。金额来自项目尚未分配的有效额度，分配本身不是再次给项目充值，也不是消费。

推荐首版规则：

- 发放有效期按企业时区的选定日期当日结束计算，表单明确显示。原型固定以 Asia/Shanghai 演示。
- 分配时选择一批来源额度，默认选最早到期且足够的一批；成员额度继承该批过期时间，不能延长原批次有效期。
- 如果一批不足但多批合计足够，提示分别分配，不静默跨批拆分。此规则与 v1.1 单次请求单来源相容。
- 批次到期后，未分配与成员尚未使用部分均不可继续使用；已消费记录保留。已准入请求按既定预占与核对规则结算。
- 新增一批额度不会延长旧额度的有效期。页面分开展示累计发放、已消费、有效待分配、成员有效余额、已过期余额。
- 经理可以在已获批项目范围内直接分配，包括给自己；如企业要限制自分配，后续可单独增加职责约束。额度申请审批仍不允许自己审批自己。

## 4. 模型资源名称与关系

推荐将三个入口放在“模型”下面，以页内分区或二级导航呈现。

| 推荐菜单名 | 回答的问题 | 内容 |
| --- | --- | --- |
| 模型目录 | 这是哪一种模型？ | 模型名称、标识、能力说明；可复用定义，不配置地址和运行限流 |
| 模型服务 | 从哪里调用？ | 内部部署平台或外部服务的名称、连接地址、凭据，以及它提供的多个模型 |
| 模型池 | 供哪些用途使用？ | 例如办公池、研发池；选择服务，再选择该服务下的具体模型；设置池的使用上限 |

“模型服务”承载用户所说的供应商对象：一个可接入的平台或服务连接。名称避免把内部部署平台误认为商业厂商。必要时可在说明中写“供应商 / 内部模型平台”。同一个供应商有多套独立地址时可登记多个服务连接。

模型目录定义与服务下模型实例分开：一个目录模型可由多个服务提供；每个服务可以挂多个目录模型，并记录上游模型标识、验证状态、计价和按需限制。同一服务模型可以加入多个用途池。

模型池是用途与使用权限的分组，不代表新建了物理算力，也不必与部门或项目一一对应。多个池引用同一服务模型时，共用其底层上限；池之间不会因为分类而获得额外算力。

首版同一池内，同一个对外模型标识只选择一个实际服务来源，避免隐式引入自动主备与负载路由。跨池可以选不同来源。

## 5. 跨对象创建：创建后回到原任务

服务向导选择目录模型时，提供“新建模型定义”。新建页面显示“创建后返回模型服务”；保存后自动勾选新模型，恢复已填地址、已选模型与其他草稿。取消只取消本次新建，不丢失原表单。

模型池选择模型服务时，同样提供“新建模型服务”；服务向导内部可以继续新建缺失的目录模型。各层返回都有明确目标，新对象保存后回填原选择。

需要区分对象是否已经保存。子对象创建成功后，即使取消父对象创建，也不能悄悄删除已保存对象；原型显示创建结果与去向。

模型验证失败保留草稿，保存与验证状态分开。新建定义不代表对应服务已实际支持该能力，仍需服务验证。

## 6. 限流建议：就近配置，集中查看

不建议要求运营人员在一个独立策略中心中先建策略、再回来绑定；也不建议在每次勾选模型时强制填写所有限流项。

| 对象 | 限制的含义 | 入口建议 |
| --- | --- | --- |
| 模型目录定义 | 无运行流量，不设置运行限流 | 仅描述能力；上下文长度是能力约束，不等于 TPM |
| 模型服务整体 | 这一连接整体可承受的容量 | 服务详情“使用限制” |
| 服务中的某个模型 | 实际模型入口的并发、RPM / TPM 等边界 | 服务下模型行“按需设置”，默认继承企业保护 |
| 模型池 | 某种用途允许的总流量 | 创建 / 编辑池内的“使用限制” |
| 人员、项目、应用 | 调用主体的公平使用与业务约束 | 各自详情，默认继承 |

普通配置使用默认保护，特殊对象才覆盖。界面必须区分“继承默认”“本级不额外限制”与“自定义上限”；本级不限制不意味着绕过上级保护。

请求必须同时满足适用的主体、用途池、服务模型、服务整体及共享资源边界。它们统计的对象范围不同，不能只计算一个数字最小值，也不能用池设置覆盖服务上限。

例如服务总上限为 100 RPM，办公池和研发池各设 80 RPM：两个池共同调用该服务时仍受服务总计 100 RPM 的约束。数字只作规则示例，不是容量建议。

在“模型”内提供“限流概览”入口，汇总对象、设置来源和上限，点击定位原对象设置；不维护第二份配置。若将来需要大量跨对象批量操作，再提升为独立一级菜单。

不同服务地址实际共享算力时仍需登记共享关系；这一共享资源保护与用途模型池分开。首版先保留必要关联，不扩成容量调度中心。

## 7. 用途池如何衔接人员、项目与应用

套餐、项目、应用选择一个模型池作为默认服务范围，必要时选池内模型子集。员工按日常或项目用途使用，不必理解供应商和路由。应用继续独立于项目。

池是治理与可用范围，不是额度账户。切换或编辑池不转移资金，也不自动发放额度。

新增池模型不自动扩大已授权的模型子集；减少、停用池中模型时展示受影响的套餐、项目和应用。原型本轮先展示池创建和项目关联，套餐及应用的完整迁移作为后续交互补齐，不宣称已经实现。

## 8. 本轮原型评审范围

新增一个聚焦“项目与模型资源”的交互原型，保留上一轮开通、员工使用和应用接入原型。重点验收：

1. 运营项目列表有创建与指定经理入口。
2. 普通员工申请创建；未审批不可分配；运营确认经理后启用；驳回可修改重提。
3. 运营发额度必须明确有效期；经理申请由运营确认后入项目。
4. 经理和运营均可分配，来源与到期日可解释，过期不能继续分配。
5. 一个服务关联多个目录模型，缺失对象可创建后返回，输入不丢失。
6. 一个池可选择多个服务下的模型；同一服务模型进入多个池仍显示共同服务上限。
7. 就近设置在限流概览中反映，无第二套策略对象。

本修订是产品设计，不固定数据库表、API 或网关底座。原型通过仅证明交互路径，不证明真实权限隔离、限流或账务一致性。
