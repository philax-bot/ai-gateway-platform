# 企业内部 AI 运营平台：企业运营能力修订 v1.3

日期：2026-10-15。当前首版范围按本文、[v1.2 项目与模型修订](token-operations-product-concept-v1.2.md)、[v1.1 易用性概设](token-operations-product-concept-v1.1.md) 顺序解释，冲突处以新版本为准。

## 1. 修订结论

组织管理、自动开通、全量密钥管理、统一审批和运行观测属于企业运营的基础能力，纳入第一版。减少必填配置和重复操作仍是设计目标；不以固定菜单数量为目标删除必要功能。

本轮明确恢复 v1.1 后置或缩减的部分：统一审批入口、全量密钥页、按组织与人员属性自动开通、全员及组织范围发放、总览与实时监控、基本故障告警。仍不引入任意表达式规则引擎、自定义多级审批流程、完整运维工单平台。

## 2. 运营菜单与责任

| 一级入口 | 页面分区 | 主要职责 |
| --- | --- | --- |
| 运营概览 | 资源、人员、用量费用、待办、活跃告警 | 看总体情况并进入下一步 |
| 模型管理 | 模型目录、模型服务、模型池、容量与保护四个独立入口 | 2026-11-11 菜单职责拆分，沿用现有业务规则 |
| 组织与成员 | 成员、组织结构 | 管归属、人员类别、业务标签、有效期和停用 |
| 开通与发放 | 开通方案、自动开通、额度发放、执行记录 | 把额度套餐、模型范围和默认限制组成开通方案，批量与自动执行 |
| 项目 | 创建、详情、额度批次、成员分配 | 延续 v1.2；审批进入统一中心 |
| 应用 | 应用详情、账目、额度、凭证与接入 | 默认记账，可选额度模式；负责人管理接入 |
| 密钥管理 | 所有个人 / 应用密钥、详情与管理记录 | 全量检索、停用 / 吊销、定位调用 |
| 审批中心 | 待我审批、已处理、我发起的、权限内全部 | 所有业务审批的统一处理入口 |
| 运行监控 | 实时状态、告警事件、告警设置 | 服务可靠性、容量和异常处置 |
| 调用日志 | 调用列表、请求详情 | 逐请求 Token、计费、结果与追溯 |

企业设置保留低频配置。通知中显示待办和告警摘要，点击仍回到统一审批或告警事件；不另建一套状态。

经理和普通员工也能进入审批中心，仅展示职责范围内的待办和个人申请。集中展示不扩大审批权限。

## 3. 统一审批中心

所有需要审批的事项在统一中心处理，包括项目创建、项目额度、个人项目额度、通用额度、应用额度和后续新增类型。业务页面可以发起申请、显示进度和提供“进入审批中心”，不另建互相独立的审批列表。

审批详情统一显示：事项类型、申请人、关联对象、申请内容、审批责任人、当前状态、处理意见、时间和生效结果。额度审批可调整批准金额及期限，明确显示申请值与批准值。

统一状态采用待审批、已批准待生效、已生效、已驳回、已撤回、执行失败、已关闭；详情保留“批准”与“生效”的区别。正常网页审批在确认后尝试执行；失败时保留批准，不显示为已发放。

| 事项 | 默认审批职责 |
| --- | --- |
| 员工申请创建项目 | 运营，确认项目经理 |
| 项目经理申请项目额度 | 运营 |
| 成员申请个人项目额度 | 当前有效项目经理；本人作为申请人或经理已停用、到期、所属组织失效时转运营 |
| 通用额度 / 应用额度 / 应用切换额度模式 | 运营（不得自批） |

管理员直接授权范围内的发放无需再审批。新增业务审批接入同一入口和记录格式，但第一版不做自定义流程设计器。重复提交 / 重复批准不能重复生效，审批人与业务对象权限变化时执行前重新核对。

2026-11-06 补充闭环规则：

- 待审批、已批准待生效、执行失败均为未完成申请；同申请人、同类型、同对象不可另建重复申请。
- 当前责任人可在影响确认后关闭已批准但未生效或执行失败的申请，必须填写原因。关闭不发放资金、不修改已有余额，保留原决定及失败记录，不能再执行或修正；申请人可重提。待审批仍用撤回或驳回，已生效不能关闭。
- 接手已批准事项必须经过“接手并核对”并留下修正记录，原批准人不能继续执行；经理恢复或负责人再变更时，执行仍按当前职责重新核对。
- 新执行在同一事务中记录实际对象、资金/预算批次、权益、实际金额、到期时间、来源/去向与当时模型名称。历史已生效申请没有回执时明确标记，不回填推断结果。
- 申请前、审批时与确认页使用共享的流程节点和变更对比；失败原因与恢复动作直接可见，规则、用户长说明与历史记录可展开。审批中心折叠表同时列出需审批事项和已有授权范围内的直接操作。
- 本轮沿用经理可从既有预算向本人分配的规则，不引入金额阈值、多级审批或记账授信上限。

## 4. 组织、成员与业务属性

基础组织支持公司 / 部门层级、上级组织和成员归属。第一版每个成员有一个主要组织；跨部门项目通过项目成员关系表达。组织停用、移动和成员调动需显示受影响范围，不能静默递归删除人员。

成员支持姓名或登录账号、主要组织、员工 / 外包等人员类别、业务标签、启用状态、有效期；外部人员保留内部责任人。人员属性由有权的运营或身份同步来源维护，员工不能通过自己修改标签获得更高额度。

第一版手动创建和批量导入均走相同的匹配及开通规则。后续目录 / SSO 同步复用这条链路；组织同步的稳定外部标识用于避免重复建人。原型只模拟手工创建和标签变更，不伪称接入企业通讯录。

## 5. 自动开通：人群条件对应开通方案

开通方案包含额度套餐（一次性 / 每月）、可用模型池与模型范围、有效期和继承的默认使用限制。原来的“额度套餐”是方案中的额度部分，不要求运营维护一套重复的钱包与授权方案。

典型规则：“正式员工”且“研发部及下级”且“具有 AI 编码标签” → 自动享用“研发月度方案”。未设置的条件视为不限制，已设置的条件为 AND。第一版提供简单的组织、类别、标签条件，不开放脚本或任意表达式。

推荐行为：

- 创建成员或可信属性更新后自动匹配。提交成员前展示命中方案及金额；规则页面可以查看受影响人数。
- 启用规则默认作用于后续新增或属性变更；存量人员需显式“预览并应用到现有成员”，避免突然全量授予。
- 同一方案经多条规则命中只授予一次；每月方案同一成员同一周期只发一次。手动开通相同方案遵守同一去重约束。
- 不同方案是否允许叠加必须明确。首版默认可叠加不同方案，预览展示每份来源与合计；无需隐藏冲突或假装只命中一条。
- 属性不再符合或规则停用时，停止由该规则维持的未来发放；本期已发额度按原期限保留。模型访问资格按仍有效的权益来源核对，人员停用则立即阻止新调用。权限调整的撤销延迟需在实施时验证。
- 成员离职、到期、停用和外部人员资格失效优先于自动开通；规则不能重新启用停用账号。
- 每次自动开通记录触发事件、命中条件、方案版本、授予结果、失败原因。失败可重试，成功对象不重复授予。

这些是轻量的人员开通规则；不同于此前后置的可任意编排的规则引擎。

## 6. 发放范围

额度发放可以选择全体有效成员、手动选择成员、某组织、某人员类别或某业务标签。组织范围明确是否包含下级；默认不含停用和已到期人员。

两类动作分开呈现：

- “开通方案”：授予可用模型与方案额度，保留周期关系。
- “临时追加额度”：发放一次性批次，明确有效期与适用模型范围；不创建永久套餐，不隐式开通未经授权的模型。

确认前显示范围说明、匹配人数、排除人数、每人额度、总金额、到期时间和人员清单。首次发放预览形成名单快照；确认前若人员或规则已变化，重新预览。发放任务有唯一批次，重复确认不重复发放，逐人结果可追溯。

“本次给研发部全部人发额度”只针对本次名单；“今后加入研发部的人自动享用方案”属于自动开通规则。界面区分两者，避免把一次发放误当持续政策。

## 7. 全量密钥管理

运营可以在权限范围内检索所有个人与应用密钥，按主体类型、所有者、组织、状态、有效期筛选。列表显示名称、脱敏前缀 / 尾号、所有者、用途、创建 / 到期 / 最近使用时间和状态。

密钥详情关联可用模型 / 池、额度主体、请求限制、调用日志、变更记录。密钥本身不单独拥有无限额度，多把密钥不能绕过同一人员或应用的总限制。

管理员无需读取明文即可停用或吊销。吊销前显示受影响主体及接入用途，要求处理原因；批量动作先显示对象清单。明文只在合法签发流程按权限一次性展示，不出现在全量列表、日志、通知或导出里。

管理员查看全量元数据不自动获得对话正文或全部密钥明文。人员停用后个人密钥立即不可用于新请求；负责人的个人停用不自动删除独立应用，但需要负责人交接。

## 8. 总览、实时监控与调用日志各司其职

运营概览显示时间范围内的请求数、输入 / 输出 / 缓存 Token、已确认费用、待核对费用记录、活跃用户 / 项目 / 应用，以及待审批和活跃告警。费用缺失不是零费用。

实时监控按服务和模型展示吞吐、并发、请求结果、TTFT / 延迟、上游故障、限流拒绝、最后更新时间与数据质量。刷新暂停、采集延迟、无流量和采集失败需分别显示；“没有错误数据”不等于服务健康。

“用量”明细入口正式改名“调用日志”。日志至少包含请求 ID、开始 / 完成时间、调用主体、组织、项目或应用、密钥脱敏标识、模型 / 池 / 服务、请求结果、Token 明细、价格依据、额度来源、实际费用、计费状态、时延、错误码及重试关联。默认不保存 / 展示提示词和输出正文。

请求成功、失败、流式中断与实际用量完整性分别表达。客户端 HTTP 200 不等于完整成功；部分输出或用量缺失应显示待核对，不能一律免费。缓存 Token 通常是输入 Token 的子集，不重复加到总 Token。

## 9. 故障指标与告警

必须明确分母，至少分开以下指标：

- 请求错误率：窗口内已结束的错误请求 / 已结束请求；排除仍在执行的请求，取消单列。
- 模型 / 上游故障率：已转发且确认上游失败的调用 / 已转发且已结束的调用；权限不足、余额不足、平台主动限流不能算成模型故障。
- 超时、网关拒绝、客户端取消、流式异常、指标采集失败各自可见，不能混成一个“模型坏了”的百分比。

推荐第一版告警配置：对象范围、指标、统计窗口、触发阈值、最小样本数、连续触发次数、恢复阈值和恢复次数。给可调整的模板与就近说明，不要求运营自己写查询表达式。

示例模板（仅供原型评审，不是已验证生产阈值）：每分钟评估最近 5 分钟；至少 20 次有效样本；上游故障率 ≥10% 连续两次触发；故障率 <5% 连续两次恢复。

规则触发后生成告警事件、站内通知，并对有权限且正在使用平台的运营人员弹窗。弹窗显示对象、实际值、阈值、窗口、样本数、首次触发时间以及“查看异常调用 / 我已知晓”。

同一对象同一规则的持续异常合并成同一事件，更新次数而非反复弹窗。“关闭弹窗”“确认知晓”“故障恢复”是不同动作：关闭不等于恢复，知晓不等于修复。恢复后再次达到条件可产生新事件。

无流量、样本不足、监控数据缺失均显示证据不足；不能因此自动解除已有告警。采集故障可作为独立告警类型。外部通知通道按客户接入，首版至少站内可用。

## 10. 原型与实施边界

本轮把组织与成员、方案 / 规则 / 范围发放、密钥、审批中心、总览、实时监控和调用日志放进一套运营原型，并保留 v1.2 项目与模型交互。演示告警可以主动推进窗口或自动模拟刷新，不访问真实平台。

当前原型不等于完整前后端实现：身份同步、真实实时指标、网关执行、真实密钥生命周期、周期调度与通知送达仍须实施和验证。核心评审目标是批量人员能否自动获得恰当权益、审批是否只需到一处、异常是否能看懂并定位到请求。

## 11. 员工端与项目成员补充（原型 v0.4）

项目详情的“项目成员与额度”区提供“添加成员”。运营与项目经理可以从有效企业成员中按姓名、组织筛选并选择多人，已加入和停用 / 到期人员不重复列出；保存形成成员关系和项目记录。加入项目不自动发钱，下一步通过“分配给成员”授予额度。普通成员仅查看自己的项目额度，不能管理其他成员。

员工端整合为：我的工作台、我的额度、接入与密钥、在线使用、我的调用日志、我的项目、审批中心。经理也有个人空间，额外按职责管理项目和审批。普通员工不必先创建项目或应用。

首次登录之后，工作台根据额度与模型访问状态给出下一步：

- 已有可用资源：查看用途与余额，办公直接在线使用，编程进入密钥接入。
- 尚未开通 / 无额度：选择日常通用或所属项目用途，提交金额与说明。日常申请同时明确模型池，由运营确认模型访问、额度和期限；项目个人额度由经理审批，经理本人申请转运营。
- 审批中：进入统一审批中心查看本人申请，不重复提交同用途待审批申请。获批后回到我的额度或工作台继续；驳回意见仍在审批详情可查。

我的额度按来源显示方案 / 批次、可用余额、有效期。日常通用额度与各项目分别选择，禁止跨用途自动补扣。同一用途中优先消费先到期的批次；过期、人员停用、模型不可用会阻止新的使用。

个人密钥绑定明确用途，填写名称和过期日期，继承该用途的模型访问与保护。一次显示完整值，确认保存后进入服务地址、模型标识和密钥填写指引；列表和后续详情只显示脱敏信息。多把密钥共享同一用途余额，运营吊销后员工侧同步失效。这里是推荐的首版交互规则，后续可根据工具接入习惯调整。

在线使用不要求员工自己创建密钥。在线模拟与密钥模拟接入都生成一条可追溯调用，成功后展示请求编号、扣费来源和剩余额度；运营全量日志与员工个人日志引用同一记录。限流或生成前失败保留输入，明确是否扣费并允许重试。

本轮演示边界：登录为无密码的企业身份模拟；密钥是无效占位值，完整值只保留在页面临时变量，不进入状态快照；成功调用固定扣 ¥0.02，不执行真实推理或按 Token 计价。仅演示同步扣费和最近 30 条本轮调用，不代表预占结算、并发扣费、完整审计留存或正式 SSO 已实现。已存在的监控窗口样本是演示数据，不与新交互调用作真实时间窗口关联。

## 12. 易用性修订（原型 v0.5）

本节覆盖前文冲突的交互默认值，完整问题与验证见 [首轮易用性检查](usability-review-v0.5.md)。

- 员工日常额度申请填写金额、使用场景和说明，不直接选择模型池；模型池由运营审批确认。项目额度仍按项目已有范围申请。
- 工作台按已开通、待审批、需申请三种状态提供下一步。在线使用不再被画成必须经过密钥创建的线性步骤；从工作台或额度页面进入使用、密钥创建时保留所选用途。
- 员工默认查看自己发起的申请，运营与经理默认查看待办。额度获批可以继续使用或恢复对应密钥草稿；项目创建和预算审批可以返回项目继续。
- 个人密钥默认有效期为当前日期起 90 天，上限为人员有效期。该默认值用于原型评审，正式部署仍需企业确定密钥策略。
- 开通方案中的模型池、自动开通规则中的方案均支持就地创建并返回；运营首次配置提供三步引导。基础使用限制继续继承，无需重复设置。
- 批量开通确认页的拟发放总额排除重复权益和无效人员，清楚列出发放 / 跳过 / 排除数量。项目成员行可直接分配额度，通用分配入口优先选中新加成员。
- 已过期通用额度保留可见记录和过期状态，不作为当前可用余额。原型旧状态不跨版本恢复，避免把旧默认值混入本轮评审。

## 13. 模型池默认值与开通范围（2026-10-16 已确认）

本节补充 v1.2 第 7 节，并覆盖前文冲突的开通交互。个人和项目使用统一的模型范围规则，项目与个人额度继续分开。

### 13.1 默认池与实际授权

在“模型 → 模型池”设置个人默认模型池、项目默认模型池。前者用于新建个人开通方案时预填，后者用于运营创建项目或审批项目创建时预填；允许两个默认值引用同一池。未设置默认值时由运营补选。修改默认值只影响之后的新建，不修改已保存的方案、项目或已授予权益；选择默认值本身不发放额度或授予权限。

模型范围有两种模式：

| 模式 | 范围 | 后续新增模型 |
| --- | --- | --- |
| 跟随模型池（默认） | 当前池内全部已开放模型 | 池变更确认生效后同步可用 |
| 仅开放指定模型 | 池内明确选中的模型 | 不自动扩大子集 |

默认展示模型池、当前已开放模型预览与跟随说明。“限制可用模型”作为按需配置；员工申请不选模型池。仅加入池但未开放、已停用、已移出的模型不能用于新调用，指定模型模式也不例外。空池或当前无已开放模型明确显示不可调用，不伪装为额度不足。

模型池变更先预览新增/关闭的模型及关联方案、已开通人员和项目，再由运营确认生效。“跟随模式”集中同步，不逐个审批；“指定模式”不扩大，但关闭或移出已选模型同样影响其新调用。保留变更记录，历史调用保留当时用途与模型。

### 13.2 个人开通方案与权益

复用“开通与发放 → 开通方案”，明确称为“个人开通方案”，包含模型池、范围模式、指定模型（如适用）、一次性/月度额度、额度期限、开通期限和默认使用限制。无需新增平行的授权方案或人员分组。新建时取个人默认池；选择已有方案时沿用方案已保存的配置。

“组织与成员 → 成员详情 → AI 使用权益”展示多项“已开通方案”。手动、批量、自动开通复用方案，并形成可追溯的人员权益记录；已开通记录保留授予时的方案版本和范围配置，池内变化按范围模式处理。修改方案模板不静默迁移存量权益；迁移必须展示影响并明确执行范围。

个人首次申请/申请新模型只填业务场景、金额和说明；运营选择方案确认开通及发放。已有权限只追加额度时选择已有权益来源，继承该来源模型范围，不重新选池、不扩权、不重复开通或触发一轮月度发放。停止未来发放与撤销模型权限是不同动作，原有额度与权益按有效期和来源状态分别核对。

2026-11-17 个人密钥套餐范围：签发时可选择全部有效个人套餐，或多选指定的已开通套餐权益。全部模式跟随后续新开通的有效权益，历史密钥保持这一行为；指定模式保存权益标识，后续新开通或重新开通的其他权益不会自动纳入。权益内部仍按原范围模式跟随模型池变更，已有授予版本和期限继续生效。模型发现、动态授权、候选路由和扣费批次必须同时限制在密钥范围内，同一公开模型标识不能绕过来源限制；指定套餐额度不足、到期或撤销时不借用范围外套餐。范围只对新请求生效，已预占调用继续按原冻结来源结算。项目和应用密钥保持各自用途隔离，不接受个人套餐范围。

### 13.3 项目创建与成员继承

运营直接创建项目时预选项目默认池，可改选或限制模型；员工申请创建项目不选池，由运营审批时取当前默认池并确认最终范围。创建与申请均必填初始额度；生效时原子建立项目及首批待分配预算，不自动形成成员余额。

项目详情提供“模型与使用范围”，由运营调整并预览成员和凭证影响；经理管理预算与成员分配。成员在该项目用途下统一继承项目范围，首版不增加逐成员模型子集。项目预算追加、成员额度审批与分配均沿用项目范围，不重新选池或隐式扩大权限。

### 13.4 使用与计费边界

可调用模型必须同时满足所选用途的有效授权、池内已开放状态及运行限制；实际消费还需存在适用于该模型的有效额度。个人多个方案不能把权限与资金任意交叉组合：扣款批次必须关联允许当前模型的权益。项目按项目范围及成员额度校验；个人凭证绑定用途，不能借用其他用途的权限或余额。

界面分别解释未开通模型、模型已停用、无有效额度和额度不足。追加金额不代表新增模型权限。池或范围变更不转移资金；项目总额度仍须分配给成员后才能使用。


### 13.5 模型服务入池与容量聚合（2026-11-05 用户澄清）

模型池按模型服务组织资源，创建时多选尚未归属其他池的服务；一个服务只归属一个池。同一模型可由池内多个服务提供，以分担请求并聚合独立服务容量。模型对使用者只展示一次，运营按服务分别管理开放状态与价格。

新请求在当前用途允许、已开放、已启用、验证通过且价格完整的来源间分流。当前实现按请求 ID 哈希排序候选服务，在准入事务内选择有可用容量的来源；某服务并发、RPM 或 TPM 已满时检查其他来源。池、用途、用户与共享算力上限继续生效。把相同底层资源登记成两个服务不代表获得两份真实算力，应配置共同的共享容量标识。

实际来源、价格及预占在准入时固定，幂等重放沿用原记录。报价版本按池、模型、三项计费基准价及非默认模型倍率标识；默认倍率 1 保留原报价版本。相同计费依据的服务可在不改变报价的情况下分流，固定报价的请求不会自动转入不同价格的来源。独立成本价不改变计费报价版本，每个请求仍冻结实际来源成本。来源选择发生在上游转发前；不增加已发出请求的自动重试或流中途切换。


## 应用计费模式（2026-11-05）

- 创建应用可选择“记账模式 / 额度模式”，默认记账模式、初始余额 0 元；额度模式创建时必填初始额度，默认空，必须大于 0。模式属于应用，多把 Key 共用同一账户与保护。
- 记账模式：模型可用且价格已配置后，签发 Key 即可调用，无需预先发放额度；按原价格预占、结算与核对，余额允许为负。模型范围、安全策略、密钥状态、调用频率和并发保护照常执行。
- 额度模式：沿用应用独立额度批次，额度不足或到期时拦截。创建时同时发放填写的初始额度；创建或发放失败一起回滚。
- 记账转额度：由应用负责人发起申请（初始额度、期限、场景、说明），企业运营审批并执行；禁止自批。提交或仅批准均不切换模式，执行时原子发放批准额度并切换。普通编辑、直接发放额度不能替代此流程。
- 用户确认历史负余额单独保留，不抵扣批准的新额度。已准入请求继续在原记账账户结算和核对；生效后的新请求使用额度批次，原 Key 保持有效。执行重试不重复发放，负责人或状态变化会使原执行失败并保留记录。
- 无模式字段的存量应用继续按额度模式运行，不自动转为允许负余额的记账模式。本次不提供额度转记账入口。


## 项目与应用额度生命周期（2026-11-06）

- 项目创建、项目创建申请、额度模式应用创建/创建申请、记账转额度申请均必填初始额度，默认空；金额为正数，最多六位小数。记账模式应用不显示额度字段。
- 新增应用创建申请由运营审批，确认模型范围；模式、负责人、组织和用途保留在申请中。禁止自批。申请、批准与实际生效分别留痕，生效后有对应对象及首批额度回执。
- 创建与首次授额在同一业务事务中执行；项目额度进入待分配预算，应用额度进入独立钱包。重复执行不重复创建/授额。既有对象普通编辑不再次授额。
- 项目和应用额度提供“指定到期日 / 长期有效”；项目默认指定日期，应用默认长期有效。日期采用北京时间当日结束。长期额度通过共享常量 `QUOTA_FOREVER` 表达，内部兼容已有非空 timestamp；界面显示“长期有效”，不显示技术日期。存量批次不迁移期限。
- 每次补充形成独立批次；不改变原金额、期限或模型范围。成员分配继承项目预算期限。继续使用现有先到期优先、单次请求须由一个批次承担预占的规则，不跨批次拼接预占。
- 运营可回收应用未使用额度或项目未分配预算，填写原因并预览；金额不得包含消费与预占。原累计授额不改写，回收单独记录。负责人/经理可申请批次延期，由运营执行；仅延长未关闭、未过期的批次，不复活过期额度。项目预算延期同步未关闭成员批次，不增加额度。
- 项目经理/运营可将成员当前未使用余额退回原来源预算，记录累计退回；预算已过期或关闭时进入预算回收记录，不恢复可用余额。
- 移出成员会关闭其项目额度、停用该项目有效 Key。当前余额成为待退回余额；已准入请求按原批次结算，后续释放也进入原批次待退回余额。经理在来源批次点击“退回原预算”处理，重新加入不自动恢复旧余额或 Key。项目结束仍统一回收未使用余额。
- 对象变更预览负责人、状态、模型范围、现有密钥与未完成申请；配置变更保留前后快照。应用交接可选择吊销旧 Key（界面默认）或明确保留；保留会提示旧负责人可能保存过完整值。旧申请执行时重新校验当前职责/状态，失败可关闭重提。
- 暂停不延期，恢复仍检查额度期限；历史调用与消费不改写。记账转额度仍保留历史账目、新额度独立使用，不提供额度转记账。
